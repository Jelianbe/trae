## 关键发现

### P0 问题（必须修复）

#### 1. 两套 CharacterManager 重复实现

- **位置**: [db_utils.py](file:///D:/trae/novel-tts-engine/db/db_utils.py#L49) vs [character_manager.py](file:///D:/trae/novel-tts-engine/pipeline/character_manager.py#L60)
- **影响**: 数据不一致风险，维护困难，连接管理模式不统一
- **现状分析**:
  - `pipeline/character_manager.py`: 使用 `threading.local()` 实现线程安全连接池，返回 `Character` dataclass，包含性别推断、活跃度管理、合并角色等丰富业务逻辑
  - `db/db_utils.py`: 每次操作创建新连接，返回 `Dict[str, Any]`，仅提供 CRUD 操作
- **建议**: 统一使用 `pipeline/character_manager.py` 作为主要实现，移除 `db/db_utils.py` 中的 `CharacterManager`
- **需要检查**: `backend/main.py` 第641行使用了 `get_char_manager()`，需确认该函数来源

---

#### 2. schema.sql 与实际建表语句不一致

- **位置**: [schema.sql](file:///D:/trae/novel-tts-engine/db/schema.sql) vs [character_manager.py#L110](file:///D:/trae/novel-tts-engine/pipeline/character_manager.py#L110-L136)
- **影响**: 数据库迁移不可控，可能导致字段缺失或冗余
- **现状分析**:
  - `schema.sql` 第5-16行已包含 `activity_weight` 和 `is_confirmed` 字段定义
  - `character_manager.py` 第128-135行通过 `ALTER TABLE` 动态添加这两个字段
  - 说明 `_ensure_tables()` 的 ALTER TABLE 逻辑在 schema.sql 更新后未清理
- **建议**: 
  1. 清理 `_ensure_tables()` 中的 ALTER TABLE 逻辑（第128-135行）
  2. 或改为使用 `init_db()` 统一从 schema.sql 建表

---

#### 3. 两种数据库连接管理模式并存

- **位置**: `pipeline/character_manager.py` (threading.local 连接池) vs `db/db_utils.py` (每次新建连接)
- **影响**: 连接泄漏风险，竞争条件，性能不一致
- **现状分析**:
  - `pipeline/character_manager.py`: 使用 `threading.local()` 存储线程本地连接，配合 WAL 模式，支持事务
  - `db/db_utils.py`: 每次操作 `get_connection()` 创建新连接并关闭，无连接池概念
  - 两处都设置 `PRAGMA journal_mode=WAL` 和 `PRAGMA foreign_keys = ON`，但其他 PRAGMA 设置不同
- **建议**: 统一连接管理模式，推荐保留 `character_manager.py` 的线程本地连接池方案

#### 5. 硬编码阈值未全部外置到 config

- **位置**: 多个 pipeline 模块
- **影响**: 不同文体/场景适应性差，调参困难
- **现状分析**:
  - `utils/config.py` 已包含 `COLD_START_CHARS_THRESHOLD`、`MAX_INPUT_CHARS`、`MAX_RESULT_CACHE_SIZE`
  - 但以下阈值仍硬编码在代码中：
    - `pipeline/pipeline_runner.py` L350: 情绪提取窗口固定为 20 字
    - `pipeline/pipeline_runner.py` L368: 对话情绪置信度阈值 0.5
    - `pipeline/pipeline_runner.py` L385: 旁白情绪置信度阈值 0.4
    - `pipeline/character_manager.py` L342: 活跃度衰减系数 0.95
    - `pipeline/character_manager.py` L392: `min_confidence` 默认 0.5
- **建议**: 将上述阈值全部移至 `utils/config.py`

---

#### 6. Pipeline 模块间存在循环导入风险

- **位置**: `pipeline/` 目录
- **影响**: 可能导致导入错误，模块耦合度高
- **现状分析**:
  - `pipeline/pipeline_runner.py` 导入了几乎所有其他 pipeline 模块
  - `pipeline/character_manager.py` 被多个模块导入（speaker_matcher, entity_linker, pipeline_runner）
  - 模块间依赖关系基本呈 DAG，但 `emotion_extractor` 和 `_emotion_tagger_legacy` 并存，容易误用
- **建议**: 
  1. 清理 `_emotion_tagger_legacy.py`，统一使用 `emotion_extractor.py`
  2. 在 `pipeline/__init__.py` 中定义模块依赖顺序

## 详细审查结果

### 1. 模块化与职责分离 - 评分: 70/100

**优点**:
- 每个模块有明确的职责（chapter_splitter, speaker_matcher, emotion_extractor 等）
- 使用工厂函数获取单例实例（`get_nlp()`, `get_character_manager()`, `get_pipeline_runner()`）
- PipelineRunner 作为调度器，不直接实现业务逻辑

**问题**:
- 两套 CharacterManager 实现职责重叠
- `_emotion_tagger_legacy.py` 和 `emotion_extractor.py` 并存，命名暗示了废弃但未清理
- `db/db_utils.py` 中的 Manager 类与 pipeline 模块中的 Manager 类职责不清

---

### 2. 数据库层规范统一 - 评分: 60/100

**优点**:
- schema.sql 定义完整，包含所有表和索引
- 使用 WAL 模式和外键约束
- `pipeline/character_manager.py` 使用线程安全的连接管理

**问题**:
- 两套 CharacterManager 实现
- 两种连接管理模式
- `_ensure_tables()` 中残留 ALTER TABLE 逻辑
- schema.sql 与 `_ensure_tables()` 的表定义不完全同步

---

### 3. 泛用性与可配置性 - 评分: 70/100

**优点**:
- 配置外置到 `utils/config.py`，支持环境变量覆盖（DB_PATH）
- 输入长度限制（MAX_INPUT_CHARS）可配置
- 缓存容量（MAX_RESULT_CACHE_SIZE）可配置

**问题**:
- 多个阈值硬编码在代码中（情绪窗口、置信度阈值等）
- 缺少文体检测机制，西幻/历史文体识别率低
- 缺少可配置的情绪词典或规则引擎

---

### 4. 接口对齐与数据流 - 评分: 75/100

**优点**:
- Pipeline 各阶段输入输出类型明确（Chapter, SentenceData, ChapterResult 等）
- `SentenceData` dataclass 包含丰富的标注信息
- 进度回调机制完善（ProgressInfo + progress_callback）

**问题**:
- SentenceData 字段命名与数据库表不一致
- speaker (字符串) 与 speaker_id (外键ID) 的转换逻辑不清晰
- 数据库缺少情绪多层标注字段（emotion_class, emotion_vector, emotion_text）

---

### 5. 测试框架与生产代码对齐 - 评分: 80/100

**优点**:
- E2E 测试覆盖全面（29 个用例）
- 后端单元测试 30/30 通过
- 测试报告格式规范，问题分类清晰

**问题**:
- 测试用例存在导航缺陷（已在 BUG-002 修复）
- 前端服务器并发能力不足（已在 BUG-004 修复）
