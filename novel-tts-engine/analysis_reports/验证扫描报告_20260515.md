### 2.2 未执行测试原因分析

**根本原因**: 每个测试类独立实例化 NLPBasics → 触发 HanLP 冷启动（~4分钟/次）。29个测试用例分布在8个测试类中，全部跑完需要约 **32分钟**。

**建议**: 在 `conftest.py` 中增加 `session` 级别的 `NLPBasics` fixture，让所有测试共享同一个 HanLP 实例，将冷启动从 N 次降到 1 次。

## 五、集成验证

### 5.1 调用链完整性

```
用户 → API → PipelineRunner → ChapterSplitter → NLPBasics → ContextDiversityValidator
                                    ↓
                              SpeakerRoleFilter
                                    ↓
                              EntityLinker
                                    ↓
                              SpeakerMatcher
                                    ↓
                              EmotionExtractor
                                    ↓
                              ChapterResult → 前端
```

**结论**: 主调用链完整。但 FO-04 (DialogueBoundaryDetector) 模块因导入失败被排除在流水线外。

### 5.2 数据流一致性

| 数据流 | 状态 | 问题 |
|--------|------|------|
| NLPResult → ContextDiversityValidator | ✅ 一致 | entities 列表逐级传递 |
| Validated → SpeakerRoleFilter | ✅ 一致 | 实体类型保持 PER |
| Filtered → EntityLinker | ✅ 一致 | 链接到角色库标准名 |
| Linked → SpeakerMatcher | ⚠️ 单向 | SpeakerMatcher 独立维护角色库，与 EntityLinker 的链接结果不共享 |
| SpeakerMatcher → EmotionExtractor | ⚠️ 部分 | 说话人结果用于情绪上下文，但不回传给角色管理器 |

**关键发现**: SpeakerMatcher 内部维护的角色活跃度状态与 EntityLinker/CharacterManager 之间缺乏同步机制。

### 5.3 前端-后端数据一致性

| 交互 | 数据格式 | 状态 |
|------|---------|------|
| 项目上传 → 章节列表 | JSON array | ✅ 一致 |
| 章节分析 → 句子结果 | JSON with speaker/emotion | ✅ 一致 |
| 角色列表 → 音色绑定 | JSON with character → voice mapping | ⚠️ 6个内置音色硬编码，未持久化到角色库 |
| TTS 生成 → 音频文件 | 二进制流 | ✅ 正常 |

## 十、总结

当前项目处于**功能可运行但结构性缺陷明显**的阶段。最需要关注的三个方向：

1. **模块可用性**: P0级缺陷导致 dialogue_boundary_detector 完全不可用，应先修复
2. **测试效率**: HanLP 冷启动是阻止开发者跑测试的核心障碍，微调 conftest.py 即可解决
3. **候选人生成**: 说话人识别准确率的根本瓶颈不在排序而在生成，需要结构性改造
