# 假设驱动开发与战略平衡 — 综合改进方案

**版本**: V1.0
**日期**: 2026-05-03
**背景**: 整合“假设驱动开发”方法与“短期/长期收益平衡”策略，建立系统化的项目治理框架
**适用范围**: 所有后续算法改动、架构优化、技术选型决策

---

## 一、为什么需要这套方案

过去几个月的迭代积累了宝贵的工程资产——92.3的NER F1、95+的对话分类、稳定的评估框架。但同时也暴露了两个结构性问题：

1. **决策缺乏方法论**：改什么、怎么改、改完怎么判断成功，全凭经验和直觉。
2. **短期收益可能排挤长期收益**：高效基线天然奖励“即刻生效”的改动，而那些需要更长时间才能体现价值的重构、泛化、统计化改造，容易被误判为无效而放弃。

这套方案的核心目的是：**在不牺牲短期交付效率的前提下，建立对长期价值的系统化保护机制。**

## 二、假设驱动开发：日常迭代的方法论

### 2.1 四步循环

```
明确目标分数 → 提出可验证假设 → 设计实验 → 接受/拒绝假设
     ↑                                              |
     └────────────────── 回退/调整 ←─────────────────┘
```

### 2.2 假设模板

每一次代码改动前，必须填写以下模板（花15分钟，保存在 `docs/假设记录/` 目录下）：

```markdown
## 假设记录 #YYYYMMDD-序号

**假设编号**: H-20260503-01
**提出日期**: 2026-05-03
**状态**: 进行中 / 已接受 / 已拒绝

### 改动内容
（一句话说清改了什么）

### 影响机制
（因果推理：为什么这个改动会导致预期效果）

### 预期效果
- 指标：斗破苍穹 NER F1
- 当前基线：92.3
- 目标值：≥92.3（不降）
- 其他约束：三份基线文本（都市、西幻、修仙）NER不降

### 验证方式
运行 `run_stability_test.py`，对比改动前后的F1和False Positives

### 回退条件
如果任一文本NER下降≥2分，立即回退

### 实验结果
（改动后填写）
- 斗破NER F1: ___
- 都市NER: ___
- 西幻NER: ___
- 修仙NER: ___
- 决策: 接受 / 拒绝
- 原因: ___
```

### 2.3 决策矩阵

| 情况 | 决策 |
|------|------|
| 目标达成，基线不降 | ✅ 接受，合并改动 |
| 目标达成，但某基线降了 | ⚠️ 拒绝，分析降分原因 |
| 目标未达成，基线不降 | ⚠️ 拒绝，记录教训 |
| 目标未达成，基线也降了 | ❌ 立即回退 |

## 三、战略平衡机制：保护长期收益

### 3.1 方案分类：速赢 vs 战略投资

每次提出假设时，必须标注方案的“投资类型”：

| 类型 | 定义 | 决策权重 |
|------|------|---------|
| **速赢** | 短期内可验证效果，改动量小，风险低 | 主要看短期指标 |
| **战略投资** | 消除技术债务、提升架构健康度、增强泛化能力，但短期指标可能不明显 | 降低短期指标要求，引入结构性健康指标 |

### 3.2 战略储备库

当一项“战略投资”方案被假设驱动流程暂时否决（短期指标不达标），但它满足以下任一条件时，**不入垃圾桶，而是存入战略储备库**：

**入库条件**：
1. **结构化优化**：消除硬编码、统一架构、修复系统设计缺陷
2. **认知增强**：赋予系统新的理解能力（如语义推理），而非增加规则
3. **上限突破**：在全新文体或压力测试上显著提升鲁棒性

**存储位置**：`docs/战略储备库.md`

**储备库条目格式**：
```markdown
## 储备方案 #YYYYMMDD-序号

**方案名称**: 统计误合并检测泛化（统计压缩率方案）
**入库日期**: 2026-05-03
**投资类型**: 战略投资
**入库原因**: 消除SINGLE_CHAR_VERBS硬编码，提升泛化能力

### 当前障碍
（为什么短期指标不足以支持立即实施）

### 启动条件
（满足什么条件时，应该重新激活这个方案）
- 条件1：硬编码密度指标超过阈值
- 条件2：新文体（历史、科幻）的NER低于75

### 预期收益
（实施后预期带来的结构性改善）
```

### 3.3 结构性健康指标体系

这些指标**不决定单次迭代的成败**，但**作为季度回顾的评估维度**，用于判断系统的长期健康度：

| 指标 | 定义 | 目标方向 | 当前值 | 每季度评估 |
|------|------|---------|--------|----------|
| **硬编码密度** | 代码中硬编码词表（黑/白名单）的数量 | 趋近于零 | 已清除FALSE_PERSON_ENDINGS，SINGLE_CHAR_VERBS待清除 | ✅ |
| **统计覆盖率** | 通过统计验证确认的实体比例 | 趋近于100% | ~70%（剩余30%依赖规则） | 每季度评估 |
| **管道纯净度** | 数据在各模块间一致传递的比例 | 趋近于100% | 已修复L2补偿覆盖问题 | ✅ |
| **文体泛化方差** | 三种文体NER得分的标准差 | 趋近于零 | 当前约15分 | 每次新文体加入后评估 |
| **技术债务率** | 代码中TODO/FIXME/HACK标记密度 | 趋近于零 | 待统计 | 每月评估 |

### 3.4 容忍缓冲带机制

对于明确标注为“战略投资”的方案，允许在**受限范围内**暂时容忍短期指标的轻微下降：

| 条件 | 限制 |
|------|------|
| **容忍幅度** | 综合分下降不超过3分 |
| **容忍时限** | 最多3轮迭代（每轮约1-2天） |
| **恢复承诺** | 实验负责人必须提供恢复路线图 |
| **否决权** | 任何基线文本下降超过5分时，立即回退，不计入容忍范围 |

## 四、日常执行流程

### 4.1 每次改动的标准操作

```
1. 提出假设（填写假设模板，标注投资类型）
      ↓
2. 运行 purity_check.py（确保无硬编码污染）
      ↓
3. 记录改动前基线（运行稳定性测试）
      ↓
4. 实施改动
      ↓
5. 运行改动后稳定性测试
      ↓
6. 对比数据，做出决策
      ↓
    ├── 接受 → 合并代码，更新文档
    ├── 拒绝（速赢） → 回退代码，记录教训
    └── 拒绝（战略投资） → 回退代码，判断是否满足入库条件
                              ├── 满足 → 存入战略储备库
                              └── 不满足 → 记录教训，不入库
```

### 4.2 月度回顾节奏

每月底进行一次30分钟回顾：

1. **战略储备库巡检**：检查是否有方案的启动条件已被满足。
2. **结构性健康指标更新**：更新硬编码密度、统计覆盖率等数据。
3. **技术债务登记**：新增了哪些临时方案？计划何时偿还？

## 七、总结

这套方案的核心价值在于：

1. **不牺牲短期效率**：假设模板只需15分钟，实验跑已有脚本，决策看一行数字。
2. **系统性保护长期价值**：战略储备库和结构性健康指标确保那些“短期不显眼、长期很关键”的方案不被遗忘。
3. **可追溯、可审计**：每一次改动都有假设文档、实验数据、决策记录。六个月后，任何接手项目的人都能理解为什么当时做了某个决定。

它不是一套束缚创造力的枷锁，而是一副让创造力更精准地抵达目标的导航仪。
