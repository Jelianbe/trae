## 三、准确率变化的真实面貌

### 3.1 历史准确率数据汇总

| 时间 | 测试集 | 评估方式 | 准确率 | 实际含义 |
|:----:|--------|---------|:------:|----------|
| V2 (5/9) | 都市异能 27 条对话 | 预创角色库(4个角色) | **76.2%** | 预创建角色下，仅都市题材 |
| V2 (5/9) | 都市异能 27 条对话 | 无角色库 | **29.6%** | 同一数据，不预创角色 |
| V4 (5/13) | 100 条 GT 基准 | 自动角色库（预创建GT角色） | **47.1%** | 多题材（都市/历史/修仙/西幻），规则基线 |
| V5 (5/14) | 100 条 GT 基准 | Hybrid 模式 | **45.1%** | 同上，+Hybrid（LLM 无效） |

### 3.2 关键认知纠正

> **76.2% 不是当前版本的退化目标，而是不同评估维度的指标**

- 76.2% 是在 **预创建角色库 + 单题材（都市）** 条件下测得的
- 47.1%~45.1% 是在 **多题材 + 自动角色** 条件下测得的
- 同一套代码在"无角色库"模式下只有 **29.6%**

**真正的退化场景是：预创角色库条件下的准确率从 76.2% 降到了什么水平？**  
——我们从未在预创建角色库条件下重新评估过当前版本。

## 四、退化根因定位（按严重程度排列）

### P0：评估口径不一致，无法直接对比

| 对比项 | V2 评估（76.4%） | 当前评估（45.1%） |
|--------|-----------------|-------------------|
| 测试集 | 都市/西幻/修仙各 25-35 段 | 51 条预提取对话（多题材混合） |
| 角色库 | 预创建 4-18 个角色 | 自动根据 GT 生成 |
| 指标 | E.11 综合分（含情绪/结构） | 纯说话人匹配准确率 |
| 测试路径 | 全 pipeline | isolate_benchmark 直接调 match_speaker |

**结论**: 45.1% 和 76.4% 之间可能**不存在实际退化**，只是测了不同的东西。

### P1：V4 引入的"只分析旁白"策略影响了上下文推理

V4 的修改（`535b7c623`）中，`get_speaker_for_sentence()` 将输入的 `text` 从完整句子改为了只传旁白：

```python
# V3 版本：传完整句子
context = DialogueContext(text=sentence, ...)

# V4 版本：只传旁白
narration = self._extract_narration(sentence)
context = DialogueContext(text=narration, ...)
```

**影响**：
- `match_speaker()` 中的 `context_reasoning` 分支只看到旁白，看不到对话内容
- 但有些关键上下文信号恰恰在对话内容中（如称呼、自称）
- 例如 "「谁！」林雪冷喝" → 背景文本只传"林雪冷喝"，对话"谁！"丢失

**修复方向**: 保留对话内容但只对说话人提取阶段做针对性过滤。

### P2：L2 语义匹配在 Pipeline 中未正确工作

V1 引入的 `semantic_ranker` 依赖：
1. `chapter_id is not None`
2. `semantic_ranker.is_available()` — 需模型加载完成

两条件同时满足才触发 L2。但在 PipelineRunner 中，首次分析时模型可能尚未加载（冷启动 47s），导致 L2 从未生效。

**修复方向**: 预加载 L2 模型，或在 PipelineRunner 初始化时主动注入。

### P3：规则系统膨胀导致置信度失真

V2→V4 的模块化增加了大量匹配路径，但每条路径的 **置信度计算缺乏统一标准**。

规则特征匹配度 ≠ 正确概率。规则在 16 条错误 case 上 confidence 0.75-0.85，但全部答错。

| ID | GT | 规则预测 | conf | 匹配路径 | 错误模式 |
|:---|:---|:---------|:----:|----------|---------|
| re_003 | 韩将军 | 将军 | 0.80 | role_core_words | "将军"是核心词，先于"韩将军"被匹配 |
| re_024 | 林雪 | 苏夜 | 0.85 | context_reasoning | 上文中"苏夜"活跃度更高，被优先选中 |
| re_037 | 药老 | 萧炎 | 0.85 | context_reasoning | 师徒场景下"萧炎"是更活跃的说话人 |
| re_064 | 亚历山大·安德森 | 骑士 | 0.80 | role_core_words | "骑士"是核心词，外国人名被截断 |

**根因**: `context_reasoning` 路径中，`_extract_context_candidates` 优先选择活跃角色，但活跃不等于正确。

### P4：模块化膨胀 → 维护复杂度 ×20

```
V0: 1 个文件 × 400 行
V5: 10+ 个文件 × 8000+ 行（含配套模块）

模块依赖链：
speaker_matcher → character_manager + nlp_basics + semantic_ranker + 
                   character_name_validator + speaker_hint_matcher + 
                   descriptive_role_extractor + self_reference_inferrer + 
                   pronoun_resolver + entity_cleaner + speech_verb_detector + 
                   speaker_matcher_interface
```

每个模块都有独立的配置、缓存、异常处理。模块间的**隐式依赖**（如 `_current_project_id` 通过 property 同步到 `rule_matcher`）导致测试和生产环境行为不一致。

### P5：Hybrid 架构中 LLM 无法介入

这是已验证的问题：
1. `analyze_dialogue()` 纯委托给 `rule_matcher`，不走 Hybrid 路径
2. 规则 confidence (0.75-0.85) 总高于 LLM_THRESHOLD (0.7)
3. LLM 候选人列表不包含上下文相关角色

## 五、复杂度评估与简化建议

### 5.1 当前架构复杂度

```
输入文本
  ↓
pipeline_runner.py (~450行)
  ↓
speaker_matcher.py (~1400行)
  ├─ _extract_narration()
  ├─ get_speaker_for_sentence()
  ├─ analyze_dialogue()
  ├─ match_speaker()          [6级漏斗，~200行]
  │   ├─ extract_speaker_hint() → hint_matcher
  │   ├─ _extract_context_candidates() → role_extractor + NER
  │   ├─ _match_from_character_library()
  │   ├─ match_by_semantic() → semantic_ranker
  │   ├─ resolve_pronoun() → pronoun_resolver
  │   └─ detect_alternating_speakers()
  ├─ _has_speech_context() → nlp_basics
  └─ backfill_unknown_speakers()
  ↓
hybrid_speaker_matcher.py (~300行)
  ├─ match_speaker() [规则→LLM 双层]
  ├─ _llm_fallback()
  ├─ _build_llm_prompt()
  └─ _parse_llm_response()
  ↓
8个配套模块（合计 ~3000 行）
```

**估算总逻辑行**: ~5000 行（实体文件），全管道 8000+ 行

### 5.2 简化方向

#### 方向 A：拆掉冗余的中间模块

当前 8 个配套模块中，真正有独立价值的是：

| 模块 | 必要性 | 理由 |
|------|:------:|------|
| `semantic_ranker` | ⚠️ 可选 | L2 兜底，但从未在 pipeline 中生效 |
| `pronoun_resolver` | ✅ 必要 | 代词消解是独立问题 |
| `entity_cleaner` | ✅ 必要 | NER 过滤是独立逻辑 |
| `character_name_validator` | ❌ 可内联 | ~50 行，可直接内联到 speaker_matcher |
| `speaker_hint_matcher` | ❌ 可内联 | ~100 行，可直接内联 |
| `descriptive_role_extractor` | ❌ 可内联 | ~170 行，逻辑较简单 |
| `self_reference_inferrer` | ❌ 可内联 | ~100 行 |
| `speech_verb_detector` | ❌ 可内联 | ~30 行常量定义 |

**合并后**: 减少 6 个文件，代码量从 5000→~3500 行。

#### 方向 B：简化 match_speaker 漏斗

当前 6 级漏斗的设计假设"多级兜底可以提高覆盖率"，实际效果却是"多级冗余输出错误"：

| 级别 | 命中数(51条) | 正确数 | 错误数 | 是否独立有效 |
|:----:|:-----------:|:------:|:------:|:-----------:|
| L1 显式提示 | 9 | 8 | 1 | ✅ |
| L2 语义(从未生效) | 0 | 0 | 0 | ❌ |
| L3 context_reasoning | 33 | 15 | **18** | ⚠️ 负收益 |
| L4 角色库 | 0 | 0 | 0 | 重复 |
| L5 NER | 0 | 0 | 0 | 重复 |
| L6 代词 | 6 | 0 | 6 | ❌ 负收益 |

**简化后**: 只保留 L1（显式提示）+ 场景特异性上下文提取（替代 L3），配合 LLM。

#### 方向 C：弱化置信度，强化 LLM

当前架构的问题是：**规则不会"示弱"**。即使不确定性很高，规则也强行输出 confidence≥0.75 的结果。

改成：
- 规则只输出"我有把握的"（LL1 显式提示 + 简单上下文）
- 不确定的都交给 LLM
- LLM 候选人列表通过上下文 NER 动态构建

## 七、消融实验与优化方向（2026-05-14 追加）

### 7.1 消融实验结果

在同一 51 条 GT 基准上运行 6 种配置的 SpeakerMatcher：

| 配置 | 正确/总数 | 准确率 | 相对 baseline |
|------|:---------:|:------:|:-------------:|
| baseline（当前版本） | 21/51 | 41.2% | — |
| 关闭 pronoun_resolver | 21/51 | 41.2% | ±0.0% |
| 关闭 role_extractor | 21/51 | 41.2% | ±0.0% |
| **关闭 NER** | **22/51** | **43.1%** | **+1.9%** |
| 传完整句子（不走旁白提取） | 21/51 | 41.2% | ±0.0% |
| 传完整句子 + 关 role_extractor | 21/51 | 41.2% | ±0.0% |

### 7.2 关键发现

**① NER 是净负收益（-1.9%）**

关闭 NER 后，准确率反而提升。原因是 NER 提取的PER实体来自旁白文本（如"族长""骑士""将军"），这些只是叙述中提到的角色，并非说话人。NER 的"上下文PER(前/后)"路径引入了比正确更多的错误。

**② role_extractor 和 pronoun_resolver 均为中性**

两者在当前基准上无净效果：
- `role_extractor` 关闭后，被"角色库旁白匹配"路径替代，结果不变
- `pronoun_resolver` 关闭后结果完全一致，说明基准中没有代词消解典型场景

**③ 旁白提取不影响基准结果**

"传完整句子"与"走旁白提取"结果逐条完全一致（0/51 差异）。说明当前 51 条 GT 中，对话内容本身不包含额外的说话人信号。

**④ 12 条"none"在所有配置中无解**

12 条一次性/描述性角色（"杀手""获救者""前辈""魔尊""女修""冒险者"等）在所有规则配置下均为 None → LLM 调用 → `unknown`。这是规则系统的硬边界。

### 7.3 45.1% 的天花板分析

当前准确率的天花板来自两个结构性矛盾：

```
51 条 GT
├─ 22 条正确（规则能稳答的）
└─ 29 条错误
   ├─ 16 条规则自信答错（conf ≥ 0.75，但全错）
   │   └─ 截断类（7条）: "将军"→"韩将军" 等
   │   └─ 错选类（9条）: "林雪"→"苏夜" 等
   ├─ 12 条规则放弃+LLM 也答不出（一次性角色）
   └─ 1 条规则放弃+LLM 答对（理论收益，实测0）
```

| 矛盾 | 问题 | 能不能修 |
|------|------|:--------:|
| 规则不会示弱 | conf 0.75-0.85 的错误不准 LLM 介入 | 调低 THRESHOLD 没用（分布重叠） |
| LLM 候选人列表差 | 候选人中不含 GT 角色，问也白问 | ✅ **可以修** |
| 1.5B 模型力不足 | 一次性角色 12/12 答不出 | 换更大模型 |
| NER 净负收益 | 引入噪声 > 提供正确信息 | ✅ **立即可以修**（关掉 NER） |

### 7.4 最大收益点排序

| # | 措施 | 预期收益 | 复杂度 |
|:--:|------|:--------:|:------:|
| 1 | **关闭 NER 的 context_per 路径**（保留 NER 用于检测新角色） | +1.9% | 🟢 低 |
| 2 | **LLM 候选人动态构建**（从 context_before/after 中 NER 提取角色优先列入） | +10%~20% | 🟡 中 |
| 3 | **换更大 LLM 模型**（Qwen2.5-3B 或 7B） | +5%~10% | 🔴 高（依赖 GPU） |
| 4 | **合并冗余模块，简化漏斗** | 维护性提升 | 🟢 低 |
| 5 | pronoun_resolver 改为全局通用实现 | 0%（对当前基准） | 🟢 低 |

## 八、关键结论

1. **版本退化假说被推翻** — V2 在统一基准上仅 21.6%，当前 45.1% 是 V4/V5 改进的结果
2. **76.2% 和 45.1% 不可直接对比** — 测试集、角色库、评估方式都不同
3. **NER 是净负收益** — 关闭 NER 后提升 1.9%
4. **核心瓶颈在于候选人列表** — 规则不会"示弱"，LLM 又被垃圾候选人拖累
5. **如果只做一件事，就是 LLM 候选人列表优化** — 其他所有措施的总收益不超过优化候选人列表的一半
