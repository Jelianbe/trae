## 一、文档体系架构

### 1.1 目录结构总览

```
novel-tts-engine/
├── docs/                          # 项目文档（开发规范、设计方案、任务计划）
│   ├── 假设记录/                   # 假设驱动开发记录 (H-XXXX)
│   ├── superpowers/plans/          # 自动化计划文档
│   ├── 项目文档索引.md             # 文档体系导航
│   ├── 开发手册_v4.0.md            # 最新开发手册
│   ├── 战略储备库.md               # 战略投资储备方案
│   └── ...
├── analysis_reports/              # 分析与报告中心
│   ├── 报告索引.md                 # 本报告（归档体系导航）
│   ├── 审查报告/                   # 代码审查、项目锐评
│   ├── 测试报告/                   # 功能测试、稳定性测试、验证测试
│   ├── 评估报告/                   # 能力评估、Pipeline 评估
│   ├── 优化报告/                   # 优化实施报告、版本对比评估
│   ├── 修复报告/                   # Bug 修复、数据修复
│   ├── 算法报告/                   # 算法设计、分析、验证
│   ├── 算法设计/                   # 方案设计、技术报告
│   ├── 情绪标注报告/               # 情绪标注专项报告与数据集
│   ├── 数据库报告/                 # 数据库优化与安全
│   ├── 评估脚本/                   # 测试脚本、评估数据、结果 JSON
│   ├── 测试原始数据/               # 测试运行原始数据
│   ├── 调查报告/                   # 根因分析报告
│   ├── 归档报告/                   # 已归档的历史报告
│   ├── 重构报告/                   # 重构实施记录
│   ├── 计划报告/                   # 开发计划与路线图
│   ├── 调试脚本/                   # 临时调试脚本
│   ├── l2集成脚本/                # L2 语义层集成脚本
│   └── 临时文件/                   # 临时输出日志（可定期清理）
├── scripts/                       # 独立脚本（测试、迁移、工具）
├── db/                            # 数据库（schema、迁移）
├── pipeline/                      # Pipeline 核心代码
├── backend/                       # 后端 API
├── frontend/                      # 前端 Web UI
├── utils/                         # 通用工具
├── tests/                         # E2E 测试
└── novel_tts.db                   # SQLite 数据库
```

### 1.2 文档分类原则

| 类别 | 存放位置 | 内容类型 | 命名规范 |
|------|---------|---------|---------|
| 开发规范 | `docs/` | 设计文档、开发手册、任务计划 | `[主题].md` |
| 审查报告 | `analysis_reports/审查报告/` | 代码审查、项目锐评 | `[主题]_[YYYYMMDD].md` |
| 测试报告 | `analysis_reports/测试报告/` | 功能测试、稳定性测试 | `[类型]_[YYYYMMDD].md` |
| 评估报告 | `analysis_reports/评估报告/` | 能力评估、Pipeline 评估 | `[主题]_[YYYYMMDD].md` |
| 优化报告 | `analysis_reports/优化报告/` | 优化实施、版本对比 | `[版本]_[主题]_[YYYYMMDD].md` |
| 修复报告 | `analysis_reports/修复报告/` | Bug 修复、数据修复 | `[模块]修复报告_[YYYYMMDD].md` |
| 算法报告 | `analysis_reports/算法报告/` | 算法设计、分析 | `[主题]_[YYYYMMDD].md` |
| 算法设计 | `analysis_reports/算法设计/` | 方案设计、技术报告 | `[方案]_[YYYYMMDD].md` |
| 情绪标注 | `analysis_reports/情绪标注报告/` | 情绪标注专项 | `[主题]_[YYYYMMDD].md` |
| 数据库报告 | `analysis_reports/数据库报告/` | 数据库优化 | `[主题]_[YYYYMMDD].md` |
| 假设记录 | `docs/假设记录/` | 假设驱动开发 | `H-[YYYYMMDD]-[序号]_[主题].md` |
| 评估脚本 | `analysis_reports/评估脚本/` | 测试脚本、评估数据 | `[action]_[target].py` |
| 临时文件 | `analysis_reports/临时文件/` | 临时输出日志（可清理） | `[临时]_[主题].txt` |

### 15.1 文件命名规范

| 类型 | 格式 | 示例 |
|------|------|------|
| 报告 | `[主题]_[YYYYMMDD].md` | `情绪标注系统评估报告_20260504.md` |

| 评估结果 | `eval_result_[test_name].json` | `eval_result_test_novel_v3.json` |
| 假设记录 | `H-[YYYYMMDD]-[序号]_[主题].md` | `H-20260503-01_管道断点修复.md` |
| 临时文件 | `[临时]_[主题].txt` | `[临时]_debug_output.txt` |

### 15.2 归档规则

1. **新建报告** → 放入对应分类子目录（审查/测试/评估/优化/修复/算法）
2. **历史报告** → 放入 `归档报告/`
3. **临时输出** → 放入 `临时文件/`，定期清理
4. **评估脚本** → 放入 `评估脚本/`
5. **评估结果 JSON** → 放入 `评估脚本/`
6. **测试原始数据** → 放入 `测试原始数据/`
7. **调试脚本** → 放入 `调试脚本/`
8. **根目录散落文件** → 定期清理，移入对应子目录

### 15.3 定期维护

| 频率 | 操作 |
|------|------|
| 每次会话结束 | 清理 `临时文件/` 中的无用输出 |
| 每周 | 检查根目录散落文件，移入对应目录 |
| 每月 | 将超过 30 天的历史报告移入 `归档报告/` |
| 每季度 | 清理 `.bak`、`.pyc`、空文件等垃圾文件 |

## 十六、归档体系改进建议

### 16.1 当前归档体系的优势

1. **目录分类清晰**：按报告类型（审查/测试/评估/优化/修复/算法）分层管理，便于快速定位
2. **命名规范统一**：`[主题]_[YYYYMMDD].md` 格式保证了文件名的可读性和排序一致性
3. **索引导航完善**：本报告作为中心索引，提供了完整的文件清单和描述
4. **维护规则明确**：定义了定期维护频率（每次会话/每周/每月/每季度），有可操作性
5. **历史归档机制**：`归档报告/` 目录有效隔离了活跃报告和历史报告

### 16.2 存在的问题

1. **文件计数不准确**：部分目录（如"临时文件"）的文件数在清理后未及时更新索引，存在信息滞后
2. **临时文件生命周期不明确**：虽然定义了"可定期清理"，但缺少清理前后的记录（如：何时删除、谁删除的、为什么删除）
3. **索引维护成本高**：每次新增/删除文件都需手动更新索引，容易遗漏
4. **跨目录关联性弱**：例如同一功能的"算法报告"和"评估报告"分散在不同目录，缺少交叉引用
5. **文件类型混杂**：情绪标注报告目录同时存放 `.md` 报告文件和 `.json.txt` 数据集文件，职责不够单一
6. **缺乏状态标记**：无法快速区分报告是"草稿"、"终稿"还是"已归档"
7. **搜索引擎不友好**：纯 Markdown 索引在文件数量增长后，查找效率会显著下降

### 16.3 改进建议

| 优先级 | 改进项 | 实施方案 | 预期效果 |
|--------|--------|---------|---------|
| P1 | 自动化索引生成 | 编写 Python 脚本 `generate_index.py`，自动扫描子目录并生成索引文件 | 消除手动维护，保证索引准确性 |
| P1 | 文件删除记录 | 在 `临时文件/` 中维护 `DELETED_LOG.md`，记录每次清理的时间、文件列表、原因 | 可追溯删除历史，避免误删 |
| P2 | 报告状态标记 | 在文件名中添加状态前缀：`[DRAFT]_`、`[FINAL]_`、`[ARCHIVED]_` | 快速识别报告成熟度 |
| P2 | 交叉引用机制 | 在相关报告开头添加 `相关报告: [链接]` 注释 | 建立报告间的知识关联 |
| P2 | 数据集分离 | 将情绪标注报告目录中的 `.json.txt` 数据集移至 `评估脚本/情绪标注数据集/` | 保持报告目录纯粹性 |
| P3 | 标签体系 | 为报告添加主题标签（如 `#情绪标注`、`#说话人识别`、`#性能优化`） | 支持多维度检索 |
| P3 | 归档触发条件 | 明确归档标准：报告完成后 30 天自动移入 `归档报告/`，或在索引中标记为 `[ARCHIVED]` | 减少手动归档决策成本 |

### 16.4 后续维护建议

1. **索引自动化（推荐优先实施）**
   - 编写脚本定期（或手动触发）扫描 `analysis_reports/` 下所有子目录
   - 自动更新索引中的文件名、日期、文件数统计
   - 输出变更摘要（新增/删除/重命名的文件）

2. **建立报告生命周期管理**
   ```
   创建 → 草稿[DRAFT] → 审核中[REVIEW] → 终稿[FINAL] → 已归档[ARCHIVED]
   ```
   - 每个报告开头添加 YAML front matter 记录状态、作者、审核日期
   - 归档时自动更新索引中的文件状态

3. **定期维护计划调整**
   - 每次会话结束：检查 `临时文件/`，记录删除操作到 `DELETED_LOG.md`
   - 每周：运行 `generate_index.py` 更新索引，检查散落文件
   - 每月：将 30 天前的 `[FINAL]` 报告移入 `归档报告/`
   - 每季度：审查归档策略，清理无价值的历史文件

4. **文档质量抽查**
   - 每月随机抽取 3-5 个报告，检查：
     - 文件是否可正常打开
     - 内容是否完整
     - 索引链接是否有效
     - 命名是否符合规范

5. **知识沉淀机制**
   - 将高质量报告中的关键结论提取为 `docs/经验总结/` 中的独立文档
   - 为常见模式（如"情绪标注验证策略"、"性能优化方法"）建立模板
   - 在索引中增加"精华报告推荐"区域，标注最值得阅读的报告
