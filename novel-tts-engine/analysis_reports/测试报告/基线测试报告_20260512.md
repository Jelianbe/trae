## 角色识别测试详情

### 关键异常

**模式A（无角色库）和模式B（预创建18角色）结果完全相同**:

| 指标 | 模式A | 模式B | 差异 |
|------|------|------|------|
| 准确率 | 58.9% | 58.9% | +0.0% |
| 加权准确率 | 60.3% | 60.3% | +0.0% |
| 正确数 | 43/73 | 43/73 | 0 |

**预创建角色库对结果无影响** — 这不正常。

### 根因诊断

通过 `diagnose_speaker.py` 和 `diagnose_diff.py` 对比 v4 备份和当前代码：

1. **代码行数差异**: v4 (1239行) vs 当前 (1248行)，但实际修改了 +465/-87 行（大量内部重构）

2. **`match_speaker` 方法关键差异**:

**v4 版本**（76.4%）:
```python
if name.startswith('未知_'):
    unknown_char = Character(id=-1, name=name, aliases=set(), gender='unknown')
    return MatchResult(character=unknown_char, confidence=confidence, ...)
```

**当前版本**（58.9%）:
```python
if name.startswith('未知_') or name == '未知':
    # 上下文推理失败（返回未知角色），不直接返回
    # 继续尝试后续的 speaker_hint 匹配（可能创建新角色）
    pass
else:
    char = self.char_manager.get_character_by_name(name, ...)
    if char:
        return MatchResult(character=char, confidence=confidence, ...)
```

**分析**: 当前版本在上下文推理失败后**不直接返回**，而是继续尝试后续的 `speaker_hint` 匹配。这理论上应该提高准确率，但实际上**可能破坏了 v4 中的匹配顺序**，导致后续匹配环节覆盖了原本正确的候选。

3. **模式A=B 的原因**: 无论是否预创建角色，SpeakerMatcher 的候选人生成逻辑不依赖角色库中的角色（而是从文本中提取），所以角色库有无不影响结果。
