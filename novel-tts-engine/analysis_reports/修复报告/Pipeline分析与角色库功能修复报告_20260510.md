## 一、已修复问题

### 修复 1: 对话去重逻辑 Bug

**问题描述**: `analyze_dialogue` 中的去重逻辑错误地丢弃了 2/6 的对话

**位置**: `pipeline/speaker_matcher.py:L1149`

**根因分析**:
```python
# 修复前（错误逻辑）
if not any(start <= p < end or p <= start < p + (end - start) for p in seen_positions):
```

`seen_positions` 存储的是之前对话的 `start` 位置，但条件中 `p <= start < p + (end - start)` 将单个位置当作区间处理，导致：
- 对话 2 `[32, 59)` 被误判为与 `[10, 26)` 重叠
- 对话 5 `[120, 140)` 被误判为与 `[103, 108)` 重叠

**修复方案**:
```python
# 修复后（正确逻辑）
seen_ranges = []  # [(start, end), ...]
for pattern in DIALOGUE_PATTERNS:
    for match in pattern.finditer(text):
        start, end = match.start(), match.end()
        dialogue = match.group(1)
        is_overlap = False
        for s, e in seen_ranges:
            if start < e and end > s:  # 标准区间重叠判断
                is_overlap = True
                break
        if not is_overlap:
            dialogues.append((start, end, dialogue))
            seen_ranges.append((start, end))
```

### 修复 4: speaker 匹配逻辑错误（context 候选人排序）

**问题描述**: 当对话前后的上下文中有多个人物时，`_extract_context_speakers` 返回的候选人列表没有按置信度排序，导致 `context_before` 的人物（conf=0.85）优先于 `context_after` 的人物（conf=0.90）被选择

**具体案例**:

| 对话 | 正确说话人 | 修复前 | 修复后 |
|------|-----------|--------|--------|
| 「嗯……我本来想宅在家打游戏...」 | 小明（suffix: "小明回答。"） | 林悦 ❌ | **小明** ✅ |
| 「没问题，我会准时到的。」 | 小明（suffix: "小明点点头。"） | 林悦 ❌ | **小明** ✅ |

**根因分析**:
1. `_extract_context_speakers` 返回的候选人列表中，`context_before` 的候选人先被添加
2. `match_speaker` 只取 `context_candidates[0]`（第一个候选人）
3. 候选人列表没有按置信度排序，导致添加顺序而非置信度决定了选择

**修复方案**:
```python
# 在 _extract_context_speakers 返回前添加排序
candidates.sort(key=lambda x: x[2], reverse=True)
```

## 五、经验教训

1. **区间重叠判断** 应该使用标准算法 `start1 < end2 and end1 > start2`，而不是自创的复杂条件
2. **数据库约束** 需要在 schema.sql 和实际数据库之间保持一致，定期检查
3. **未知值判断** 应该同时检查 `'未知'` 和 `'未知_xxx'` 两种格式
4. **上下文优先级** `context_after`（对话后的旁白）通常比 `context_before` 更明确地指示说话人，需要通过置信度排序确保正确选择
5. **候选人列表** 返回前必须按置信度排序，不能依赖添加顺序
