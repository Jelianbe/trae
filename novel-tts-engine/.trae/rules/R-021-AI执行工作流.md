# R-021-AI执行工作流（v2.0）

## 触发场景
当用户发出以下任何指令时，必须启动"AI 执行工作流"：

- 任何涉及算法模块的代码修改（说话人识别 / 情绪提取 / NER 增强）
- "改造"、"优化"、"修复"、"执行改动"等关键词
- 任何要求改动 pipeline/ 或 tests/ 中算法逻辑的指令

## 工作流路径

严格遵循 `docs/AI执行工作流_算法迭代标准手册.md` 中的流程。

## 第-1步：优先级裁定（新增）

在执行任何算法模块改动前，AI 必须先执行优先级裁定。

### 裁定流程

1. 检查 `analysis_reports/` 目录下是否存在最新扫描报告（文件名含当前或最近日期）
2. 如果存在扫描报告，按以下优先级顺序裁定本次迭代应处理的问题：
   - **P0 功能缺陷**（模块不可用/导入失败）→ 最高优先级
   - **P0 性能瓶颈** → 次高优先级
   - **P0 代码质量缺陷** → 高优先级
   - **P1 代码质量缺陷** → 中优先级
   - **测试覆盖度缺失** → 中优先级
   - **结构性改进** → 按需处理
3. 如果不存在扫描报告，跳过第-1步，直接从第0步开始
4. 如果用户指令指定的改动不在扫描报告优先级首位，AI 必须告知用户优先级偏离情况，并等待用户确认后再继续

### 裁定产出

- 任务类型（P0紧急修复 / 性能优化 / 代码质量治理 / 结构性改造）
- 问题编号列表（如 PERF-P0-1、QUAL-P1-3）
- 当前是否有未处理的 P0 问题（是/否）

---

## 入口判断强制约束

开始改动前，AI 必须先回答：

```
□ 是否读了 docs/AI执行工作流_算法迭代标准手册.md？（必须是 v2.0 版）
□ **是否先执行了第-1步（优先级裁定）？**
□ **是否先做了第0步（备份）？——先存再改，不可跳过**
□ 当前任务类型是什么？（P0紧急修复 / 性能优化 / 代码质量治理 / 结构性改造）
□ 如果任务类型不是 P0 紧急修复，当前是否有未处理的 P0 问题？（有→必须先处理P0）
□ 假设模板中"可证伪条件"是否已填写（必填项，禁止写"准确率下降就回退"这类废话）？
□ 假设模板是否已保存到 docs/假设记录/ 目录？
□ 如果是批量执行模式，是否确认文件不重叠且风险均为"低"？
```

八项全部为"是"才能继续。

## 步骤摘要

| 步骤 | 内容 | 产出 |
|:----:|------|------|
| **-1** | **优先级裁定（新增）** | **任务类型 + 问题编号列表** |
| **0** | **快照备份（先存再改）** | **备份目录 + 路径记录到假设文档** |
| 1 | 入口判断 + 假设模板（含可证伪条件） | docs/假设记录/H-日期-序号.md |
| 2 | v7.0 合规检查（7项原则） | 通过 / 重新设计 |
| 3 | 基线锁定（分布拆解） | 写入 analysis_reports/基线记录.md |
| 4 | 执行改动（按任务类型路由） | 代码修改 |
| 5 | 验证（分布拆解对比） | 改后数据 |
| 5.5 | 过拟合检查（每3轮） | 留出集方向判定 |
| 6 | 决策矩阵 + 储备库判断 | 接受/拒绝/入库/待观察 |

## 任务类型模板（新增）

根据第-1步裁定的任务类型，选择对应的执行路径和验收标准。

### P0紧急修复
- **执行路径**: 第-1步 → 第0步 → 第1步（简化假设模板）→ 第3步 → 第4步 → 第5步 → 第6步
- **跳过**: v7.0 合规检查（第2步），P0 修复以恢复功能为优先
- **改动原则**: 最小改动原则，只修改有问题的代码行
- **模板**: 修复问题 <问题编号>：<3行以内的改动说明>
- **验收标准**: 模块可导入 + 功能恢复 + 不破坏上下游测试

### 性能优化
- **执行路径**: 第-1步 → 第0步 → 第1步 → 第3步（必须含基准时间）→ 第4步 → 第5步（必须含耗时对比）→ 第6步
- **改动原则**: 性能优先，可适度增加复杂度
- **模板**: 优化 <问题编号>：<优化策略说明>
- **验收标准**: 性能提升 ≥ 50%（P0）/ ≥ 30%（P1）/ 有明确耗时对比数据 + 功能无退化

### 代码质量治理
- **执行路径**: 第0步 → 第4步 → 第5步（验证编译通过 + 测试无回归）
- **改动原则**: 保持语义不变，只重构结构
- **模板**: 治理 <问题编号>：<治理方式说明>
- **验收标准**: git diff 确认无逻辑变更 + 测试全部通过 + 无新增告警
- **可合并**: 多个代码质量治理任务可走批量执行模式

### 结构性改造
- **执行路径**: 完整 7 步流程（第0步→第6步），第2步（v7.0合规检查）为强约束
- **改动原则**: 需要预设计，先写设计文档再改代码
- **模板**: 改造 <改造目标>：<设计说明>
- **验收标准**: 设计文档审核通过 + 结构拆分后功能无退化 + 历史测试全部通过

## 强制约束

1. **每轮迭代先备份（第0步不可跳过）**：备份未完成 → 不能进入第1步
2. **基线必须分布拆解**：不能只记总准确率，必须按挑战类型 + 文体拆解（见第3步示例）
3. **决策阈值与测试集规模挂钩**：51 条基准显著提升 ≥ 3.9%（≥2条），100 条基准 ≥ 2.0%（≥2条）
4. **可证伪条件必填**：假设模板中如果"可证伪条件"为废话或空，退回重填
5. **v7.0 违规强拦**：原则2（不猜）和原则5（决策权隔离）违规必须重新设计
6. **硬编码禁止**：新增静态词表必须有来源注释，禁止 A→B 映射表
7. **所有决策必须入基线记录**：不记录=没发生

## 步骤4：执行改动路由

第4步（执行改动）根据任务类型选择不同的执行路径：

```
┌─ P0紧急修复：最小改动原则，只修改有问题的代码行
│  模板：修复问题 <问题编号>：<3行以内的改动说明>
│  验收：模块可导入 + 不破坏上下游测试
│
├─ 性能优化：性能优先，可适度增加复杂度
│  模板：优化 <问题编号>：<优化策略说明>
│  验收：耗时对比数据 + 功能无退化
│
├─ 代码质量治理：保持语义不变，只重构结构
│  模板：治理 <问题编号>：<治理方式说明>
│  验收：git diff 确认无逻辑变更 + 测试全部通过
│
└─ 结构性改造：需要预设计，先写设计文档再改代码
   模板：改造 <改造目标>：<设计说明>
   验收：设计文档审核通过 + 改造后测试覆盖
```

## 步骤6：决策矩阵

第6步（决策矩阵 + 储备库判断）的决策规则如下：

| 执行模式 | 结果 | 决策 |
|---------|------|------|
| 单次迭代 | 目标达成，基线不降 | ✅ 接受 |
| 单次迭代 | 目标达成，但某基线降了 | ⚠️ 拒绝，分析降分原因 |
| 单次迭代 | 目标未达成，基线不降 | ⚠️ 拒绝，记录教训 |
| 单次迭代 | 目标未达成，基线也降了 | ❌ 立即回退 |
| **批量执行** | **全部通过** | **✅ 全部接受** |
| **批量执行** | **部分通过** | **⚠️ 接受通过的，回滚失败的，记录失败原因** |
| **批量执行** | **全部失败** | **❌ 全部回滚，分析根因** |

## 批量执行模式（新增）

当多个低风险任务同时存在时，可合并为一次批量执行。

### 触发条件
以下条件**全部满足**时，可开启批量执行模式：
- 待执行任务 ≥ 2 个
- 每个任务均为代码质量治理类型（P1/P2）
- 每个任务改动范围不重叠（不同文件）
- 每个任务的风险评估为"低"

### 执行流程
```
第0步（统一备份全部涉及文件）
  ↓
按文件逐个执行第4步（每个文件独立修改）
  ↓
统一验证（运行全部测试）
  ↓
决策矩阵判定（全部通过 / 部分通过 / 全部失败）
```

### 失败处理
- 批量执行中有部分任务失败时：自动从第0步备份恢复失败的文件
- 已成功的任务保留不动
- 失败任务记录到 TASKS.md，标记为"阻塞"

## 任务清单与扫描报告双向绑定（新增）

每次迭代开始前，AI 必须将 TASKS.md 与扫描报告的问题清单进行双向绑定。

### 绑定规则
- 根据扫描报告创建新任务时，必须在 TASKS.md 中引用问题编号（如 PERF-P0-1、QUAL-P1-3）
- 任务描述必须包含"修复问题 [问题编号]: [问题简述]"
- 任务完成时，在 TASKS.md 中标注"已修复"，并记录验证方式

## 与改造方案的关系

每次迭代应引用 docs/ 下对应的改造方案文档，按方案中的具体改动说明执行第4步。

## 优先级

最高优先级 - 所有算法模块迭代必须遵循本工作流
