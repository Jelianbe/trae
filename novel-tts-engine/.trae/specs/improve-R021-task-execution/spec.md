# R-021 任务清单与执行方法改进 Spec

## Why

当前 R-021（AI执行工作流 v2.0）定义了算法迭代的标准 7 步流程（第0步→第6步），但**验证扫描报告_20260515** 揭示了 1 个 P0 模块缺陷、4 个 P0 性能瓶颈、1 个 P0 代码质量问题、11 个 P1 代码质量问题、14 个无测试覆盖模块等系统性问题。R-021 缺乏以下能力：

1. **无任务分类机制**：P0 紧急修复、性能优化、代码质量治理、结构性改造全部走同一流程，没有区分处理
2. **无批量执行方法**：每次迭代只处理一个问题，导致 16 项修复如果串行执行大约需要数十次独立迭代
3. **无扫描报告集成**：R-021 不包含与 `analysis_reports/` 目录下扫描报告的联动机制
4. **任务粒度不匹配**：现有步骤是为单次算法改动设计的，没有处理大范围治理任务的分解方法

## What Changes

### 新增内容

1. **新增「第-1步：优先级裁定」**：在执行任何迭代之前，先读取最新扫描报告，对发现的问题按优先级裁定处理顺序
2. **新增「任务类型模板」**：定义 4 种任务类型（P0紧急修复、性能优化、代码质量治理、结构性改造），各有不同的执行路径和验收标准
3. **新增「批量执行模式」**：当多个低风险（P2+或第一阶段）任务同时存在时，可合并为一次批量执行
4. **新增「任务清单管理」**：每次迭代开始前先更新 TASKS.md，与扫描报告问题清单进行双向绑定

### 修改内容

1. **改造入口判断约束**：增加扫描报告检查项（"是否有未处理的 P0 问题？"）
2. **改造步骤摘要**：步骤4（执行改动）增加任务类型路由逻辑
3. **改造决策矩阵**：增加"批量执行"的决策路径

### 移除内容

无移除。

## Impact

- **Affected specs**: R-021 工作流规则本身
- **Affected code**: `.trae/rules/R-021-AI执行工作流.md`
- **Affected systems**: AI 执行工作流的入口判断、任务路由、执行方法
- **Related docs**: `analysis_reports/` 目录下的扫描报告、`TASKS.md`

## ADDED Requirements

### Requirement: 第-1步 - 优先级裁定

The system SHALL add a new step (indexing as "Step -1") before Step 0, named "优先级裁定".

#### Scenario: 正常流程
- **WHEN** AI 收到算法模块改动指令
- **THEN** AI 必须先检查 `analysis_reports/` 目录下是否有最新扫描报告
- **AND** 如果存在扫描报告，必须按以下优先级裁定处理顺序：
  1. P0 功能缺陷（模块不可用/导入失败）
  2. P0 性能瓶颈
  3. P0 代码质量缺陷
  4. P1 代码质量缺陷
  5. 测试覆盖度缺失
  6. 结构性改进

#### Scenario: 扫描报告不存在
- **WHEN** `analysis_reports/` 目录下无扫描报告
- **THEN** AI 跳过第-1步，直接从第0步开始

#### Scenario: 当前指令与扫描报告冲突
- **WHEN** 用户指令指定的改动不在扫描报告优先级首位
- **THEN** AI 必须告知用户优先级偏离情况，并等待用户确认后再继续

---

### Requirement: 任务类型模板

The system SHALL define 4 种任务类型模板，每种有独立的执行路径和验收标准。

#### Scenario: P0紧急修复
- **WHEN** 任务类型为 P0 紧急修复
- **THEN** 执行路径为：第-1步 → 第0步 → 第1步（简化模板）→ 第3步 → 第4步 → 第5步 → 第6步
- **AND** 跳过 v7.0 合规检查（第2步），因为 P0 修复以恢复功能为优先
- **AND** 验收标准为：模块可导入/功能恢复/不影响上下游

#### Scenario: 性能优化
- **WHEN** 任务类型为性能优化
- **THEN** 执行路径为：第-1步 → 第0步 → 第1步 → 第3步（必须含基准时间）→ 第4步 → 第5步（必须含耗时对比）→ 第6步
- **AND** 验收标准为：性能提升 ≥ 50%（P0）/ ≥ 30%（P1）/ 有明确数据

#### Scenario: 代码质量治理
- **WHEN** 任务类型为代码质量治理
- **THEN** 执行路径为：第0步 → 第4步 → 第5步（验证编译通过+测试无回归）
- **AND** 可合并为批量执行（见批量执行模式）
- **AND** 验收标准为：代码风格规范通过/测试全部通过/无新增告警

#### Scenario: 结构性改造
- **WHEN** 任务类型为结构性改造
- **THEN** 执行完整 7 步流程（第0步→第6步），且第2步（v7.0合规检查）为强约束
- **AND** 验收标准为：结构拆分后功能无退化/历史测试全部通过

---

### Requirement: 批量执行模式

The system SHALL support 批量执行模式，当多个低风险任务同时存在时可合并为一次执行。

#### Scenario: 批量执行条件
- **WHEN** 以下条件全部满足：
  - 待执行任务 ≥ 2 个
  - 每个任务均为代码质量治理类型（P1/P2）
  - 每个任务改动范围不重叠（不同文件）
  - 每个任务的风险评估为"低"
- **THEN** 可合并为一次批量执行

#### Scenario: 批量执行流程
- **WHEN** 批量执行模式开启
- **THEN** 执行路径为：第0步（统一备份）→ 批量修改（按文件逐个执行第4步）→ 统一验证（全部测试）
- **AND** 决策矩阵按"全部通过/部分通过/全部失败"三个路径

#### Scenario: 批量执行失败处理
- **WHEN** 批量执行中有部分任务失败
- **THEN** 自动回滚失败的任务（从第0步备份恢复）
- **AND** 已成功的任务保留
- **AND** 记录失败任务到 TASKS.md 标记为阻塞

---

### Requirement: 任务清单与扫描报告双向绑定

The system SHALL maintain bidirectional binding between TASKS.md and scanning reports.

#### Scenario: 新增任务
- **WHEN** AI 根据扫描报告创建新任务
- **THEN** 必须在 TASKS.md 中引用问题编号（如 PERF-P0-1、QUAL-P1-3）
- **AND** 任务描述中必须包含"修复问题 [问题编号]: [问题简述]"

#### Scenario: 任务完成
- **WHEN** 一个根据扫描报告创建的任务完成
- **THEN** 必须在 TASKS.md 中标注"已修复"，并记录验证方式

## MODIFIED Requirements

### Requirement: 入口判断强制约束（改造）

改造入口判断约束，增加扫描报告检查项：

**旧版：**
```
□ 是否读了 docs/AI执行工作流_算法迭代标准手册.md？（必须是 v2.0 版）
□ **是否先做了第0步（备份）？——先存再改，不可跳过**
□ 是否从"第0步"开始，没有跳过任何步骤？
□ 假设模板中"可证伪条件"是否已填写（必填项，禁止写"准确率下降就回退"这类废话）？
□ 假设模板是否已保存到 docs/假设记录/ 目录？
```

**新版：**
```
□ 是否读了 docs/AI执行工作流_算法迭代标准手册.md？（必须是 v2.0 版）
□ **是否先执行了第-1步（优先级裁定）？**
□ **是否先做了第0步（备份）？——先存再改，不可跳过**
□ 当前任务类型是什么？（P0紧急修复 / 性能优化 / 代码质量治理 / 结构性改造）
□ 如果任务类型不是 P0 紧急修复，当前是否有未处理的 P0 问题？（有→必须先处理P0）
□ 假设模板中"可证伪条件"是否已填写（必填项，禁止写"准确率下降就回退"这类废话）？
□ 假设模板是否已保存到 docs/假设记录/ 目录？
□ 如果是批量执行模式，是否确认文件不重叠且风险均为"低"？
```

### Requirement: 步骤4 - 执行改动（改造）

改造步骤4（执行改动），增加任务类型路由逻辑：

**旧版：** 无路由逻辑，所有改动走同一路径

**新版：**
```
执行改动（第4步）——根据任务类型选择执行路径：

┌─ P0紧急修复：最小改动原则，只修改有问题的代码行
│  模板：修复问题 <问题编号>：<3行以内的改动说明>
│  验收：模块可导入 + 不破坏上下游测试
│
├─ 性能优化：性能优先，可适度增加复杂度
│  模板：优化 <问题编号>：<优化策略说明>
│  验收：耗时对比数据 + 功能无退化
│
├─ 代码质量治理：保持语义不变，只重构结构
│  模板：治理 <问题编号>：<治理方式说明>
│  验收：git diff 确认无逻辑变更 + 测试全部通过
│
└─ 结构性改造：需要预设计，先写设计文档再改代码
   模板：改造 <改造目标>：<设计说明>
   验收：设计文档审核通过 + 改造后测试覆盖
```

---

### Requirement: 步骤6 - 决策矩阵（改造）

改造步骤6（决策矩阵），增加"批量执行"的决策路径：

| 执行模式 | 结果 | 决策 |
|---------|------|------|
| 单次迭代 | 目标达成，基线不降 | ✅ 接受 |
| 单次迭代 | 目标达成，但某基线降了 | ⚠️ 拒绝，分析降分原因 |
| 单次迭代 | 目标未达成，基线不降 | ⚠️ 拒绝，记录教训 |
| 单次迭代 | 目标未达成，基线也降了 | ❌ 立即回退 |
| **批量执行** | **全部通过** | **✅ 全部接受** |
| **批量执行** | **部分通过** | **⚠️ 接受通过的，回滚失败的，记录失败原因** |
| **批量执行** | **全部失败** | **❌ 全部回滚，分析根因** |
