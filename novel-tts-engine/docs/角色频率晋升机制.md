# 角色频率晋升机制

> **文档类型**: 独立方案 · 角色生命周期管理  
> **创建日期**: 2026-05-16  
> **关联**: SRL_ARG0提取方案（角色发现）、别名匹配Bug修复方案（Bug ⑥ 质量门禁）  
> **问题**: 临时角色一创建就直接写入 SQLite，与正式角色无区分，频率晋升无从谈起

---

## 一、现状诊断

### 当前流程

```
SRL/NER/规则发现 "报信者"
  ↓
_match_candidate_to_character("报信者")
  → 未匹配 → _register_temporary_character("报信者")
    → char_manager.add_character(name="报信者")     ★ 直接写 SQLite
    → self._temp_char_cache["报信者"] = char         ★ 内存缓存
```

**三个问题**：

1. **无 temp/permanent 区分** — SQLite 中所有角色平等，无法判断谁是"临时发现的"
2. **无频次跟踪** — 角色出现了 20 次和 1 次，在数据库层面无差别
3. **无晋升路径** — 一次性路人角色和主要角色地位相同，参与候选池竞争

### 后果

- 一次性角色（服务员、路人、报信者）与主要角色在候选池中平等竞争
- 每个 chapter 结束时，`reset_activity()` 只清空内存缓存，不清理数据库
- 长期运行导致角色库膨胀，候选池信噪比下降
- **战略储备库中记录的"短文本推理 + 长文本频率分析"方案** 一直无法落地

---

## 二、方案设计

### 2.1 核心概念

```
角色按生命周期分三个状态：

┌──────────┐     mention_count >= N     ┌──────────┐
│  临时角色  │ ───────────────────────→ │  正式角色  │
│  (temp)   │                           │ (正式)   │
│  不入SQLite│                           │  SQLite  │
│  内存+in-memory DB │                     │  持久化  │
└──────────┘                           └──────────┘
       │
       │ chapter 结束时，mention_count < N
       ↓
   自动清理（无痕迹）
```

- **临时角色（Temp）**：SRL/NER/规则发现的陌生角色名，仅存在于当前 chapter 内存中，不入 SQLite 主表
- **正式角色（Permanent）**：通过频率验证的角色，持久化到 SQLite，跨 chapter 可用
- **晋升条件**：mention_count >= PROMOTION_THRESHOLD（默认 3）

### 2.2 数据模型

在 `CharacterManager` 中新增内存结构，不修改 SQLite Schema：

```python
class CharacterManager:
    def __init__(self, ...):
        # 原有持久化存储...
        
        # ★ 新增：临时角色存储（name -> TempCharacterInfo）
        # 只存在于当前 chapter 的 analyze_dialogue 生命周期内
        self._temp_chars: Dict[str, TempCharacterInfo] = {}
        
        # ★ 新增：正式角色的频次计数器（name -> count）
        # 角色名在文中每出现一次，计数器 +1
        self._frequency: Dict[str, int] = {}
```

`TempCharacterInfo` 数据类：

```python
@dataclass
class TempCharacterInfo:
    name: str
    mention_count: int = 0      # 当前 chapter 中出现次数
    project_id: int = 0
    gender: str = 'unknown'
    first_seen_at: int = 0      # 首次出现的句子索引
```

### 2.3 API 设计

在 `CharacterManager` 中新增以下方法：

```python
# ───── 临时角色 ─────

def add_temp_character(self, name: str, project_id: int,
                       gender: str = 'unknown') -> bool:
    """注册临时角色（不入 SQLite）。

    跨章节继承：如果 _frequency 中已有此角色名
    （上一个章节出现过但未达标），作为初始计数。
    """
    if name in self._temp_chars:
        return False

    # 检查跨章节频次历史（_frequency 随 cleanup 不清空）
    prev_count = self._frequency.get((name, project_id), 0)

    self._temp_chars[name] = TempCharacterInfo(
        name=name, project_id=project_id, gender=gender,
        mention_count=prev_count,  # 继承跨章节累计
        first_seen_at=datetime.now()
    )

    # 如果历史频次已达阈值，直接晋升
    if prev_count >= PROMOTION_THRESHOLD:
        self._promote_temp_character(name, project_id)

    return True

def get_temp_character(self, name: str) -> Optional[TempCharacterInfo]:
    return self._temp_chars.get(name)

def get_all_temp_characters(self) -> List[TempCharacterInfo]:
    return list(self._temp_chars.values())

# ───── 频次 ─────

def increment_frequency(self, name: str, project_id: int):
    """角色名频次 +1。同时检测临时角色是否达到晋升阈值。

    _frequency 字典跨章节存活，不随 cleanup 清空。
    """
    key = (name, project_id)
    self._frequency[key] = self._frequency.get(key, 0) + 1

    # 检测临时角色晋升
    if name in self._temp_chars:
        self._temp_chars[name].mention_count += 1
        if self._temp_chars[name].mention_count >= PROMOTION_THRESHOLD:
            self._promote_temp_character(name, project_id)

def get_frequency(self, name: str, project_id: int) -> int:
    return self._frequency.get((name, project_id), 0)

def get_frequency_map(self, project_id: int) -> Dict[str, int]:
    """获取项目中所有角色的频次映射。"""
    return {
        name: count
        for (name, pid), count in self._frequency.items()
        if pid == project_id
    }

# ───── 晋升 ─────

def _promote_temp_character(self, name: str, project_id: int):
    """将临时角色晋升为正式角色（写入 SQLite）。"""
    temp_info = self._temp_chars.get(name)
    if not temp_info:
        return None

    char = self.add_character(
        name=name,
        project_id=project_id,
        aliases=set(),
        gender=temp_info.gender
    )
    if char:
        logger.info(f"临时角色晋升: {name} (提及{temp_info.mention_count}次)")
        del self._temp_chars[name]
    return char

# ───── 清理 ─────

def cleanup_temp_characters(self):
    """章节结束时清理不达标的临时角色。

    不设 promote_all 参数——避免"章节末尾大赦"绕过阈值。
    未达标角色记录日志后清除；_frequency 保留，跨章节累计。
    """
    below = [
        info for info in self._temp_chars.values()
        if info.mention_count < PROMOTION_THRESHOLD
    ]
    if below:
        logger.debug(f"清理未达标临时角色: "
                     f"{[(t.name, t.mention_count) for t in below]}")
    self._temp_chars.clear()  # 清空临时角色，_frequency 保留
```

### 2.4 频次递增钩子

在现有调用路径中插入 `increment_frequency` 钩子：

| 路径 | 位置 | 触发条件 |
|:----|:-----|:---------|
| **NER PER 提取** | `_extract_from_ner()` 中每次提取角色后 | 每提取一个 PER 实体 |
| **语境角色匹配** | `_extract_context_speakers()` 语境优先路径 | 每次角色被命中 |
| **临时角色创建** | `_register_temporary_character()` 创建后 | 首次创建 |
| **说话人匹配成功** | `match_speaker()` 返回角色后 | 每确定一次说话人 |
| **SRL ARG0 提取** | SRL 步骤2.5 加入候选池后 | 每次 SRL 提取到 |

```python
# 示例：在 match_speaker 返回角色后
def match_speaker(self, ...):
    char = ...
    if char:
        self.char_manager.increment_frequency(char.name, self._current_project_id)
    return char
```

## 三、与 SRL 角色发现的关系

SRL 是当前**临时角色的主要生产者**。SRL 在 `analyze_dialogue()` 开头扫描全文时，会按以下流程走：

```
SRL 扫描全文，提取所有 ARG0
  ↓
_normalize_srl_arg0() → 去修饰 + 去头衔 + 非人物过滤
  ↓
角色库匹配 → 未匹配 → 注册临时角色 add_temp_character()
  ↓
后续对话中每次提及 → increment_frequency()
  ↓
mention_count >= 3 → _promote_temp_character() → 写入 SQLite
```

这解决了之前 SRL 方案中的一个遗留问题：**SRL 发现的陌生角色应该以什么方式进入角色库？**

之前是 `_register_temporary_character` 直接写 SQLite，没有质量控制。现在改为 `add_temp_character`（不入 SQLite）+ 频次晋升，相当于给 SRL 角色发现加了一个"实习期"。

## 四、与现有代码的兼容性

### 4.1 `_register_temporary_character` → 改为调用 `add_temp_character`

```python
def _register_temporary_character(self, name, context, skip_speech_check=False):
    if not skip_speech_check and not self._has_speech_context(context):
        return None
    
    # ★ 改为：先查临时角色库，再查正式角色库
    temp_info = self.char_manager.get_temp_character(name)
    if temp_info:
        return temp_info  # 返回临时角色引用
    
    # 查正式角色库
    char = self.char_manager.get_character_by_name(name, self._current_project_id)
    if char:
        return char
    
    # 注册临时角色（不入 SQLite）
    try:
        gender = self._infer_gender_from_context(name, context)
        self.char_manager.add_temp_character(name, self._current_project_id, gender)
        logger.debug(f"注册临时角色: {name} (性别: {gender})")
        return self.char_manager.get_temp_character(name)
    except Exception as e:
        logger.warning(f"注册临时角色失败: {name}, {e}")
        return None
```

### 4.2 候选池匹配 → 同时查正式 + 临时

```python
def get_all_character_names(self, project_id: int) -> Set[str]:
    """返回所有可匹配的角色名（正式 + 临时）。"""
    names = set()
    # 正式角色
    for char in self.get_all_characters(project_id):
        names.add(char.name)
        names.update(char.aliases)
    # 临时角色
    for info in self._temp_chars.values():
        if info.project_id == project_id:
            names.add(info.name)
    return names
```

### 4.3 `reset_activity()` → 新增 `cleanup_temp_characters()`

```python
def reset_activity(self):
    self._character_activity.clear()
    self._recent_speakers.clear()
    self._recent_mentions.clear()
    self._temp_char_cache.clear()
    
    # ★ 新增：清理临时角色

```

### 4.4 `get_eligible_characters()` → 整合频次（替代 H-20260516-10）

原本 H-20260516-10 的方案是"过滤候选项"（min_freq < 5 不参与匹配），被拒绝是因为测试集没有动态角色发现场景。现在有了 SRL 角色发现和临时角色晋升，频次过滤有了实际作用场景。

但在正式角色和临时角色之间，候选排序逻辑应该区分优先级：

```python
# 在候选池排序中
for char_name in candidate_names:
    char = self.char_manager.get_character_by_name(char_name, project_id)
    temp_info = self.char_manager.get_temp_character(char_name)
    
    if char:  # 正式角色
        confidence = base_confidence  # 正常置信度
    elif temp_info:  # 临时角色
        # 临时角色置信度 = base * (mention_count / PROMOTION_THRESHOLD)
        ratio = temp_info.mention_count / PROMOTION_THRESHOLD
        confidence = base_confidence * min(ratio, 1.0)
    else:
        confidence = base_confidence * 0.5  # 低分
```

这样临时角色不会因为"刚出现一次"就以完整置信度参与候选竞争，而是随着出现次数增加逐步获得更高置信度。

## 七、与现有方案的集成顺序

此方案是**独立于四刀 Bug 修复和 SRL 接入的补充机制**。建议执行顺序：

```
前三刀：Bug 修复（恢复基线）
第四刀：SRL ARG0 接入（新信号源）
第五刀：角色频率晋升机制（角色生命周期管理）
```

也可以先做第五刀，再做第四刀——因为 SRL 是临时角色的主要生产者，先有频率晋升机制，SRL 发现的角色才有干净的生命周期管理。建议顺序是：**第一刀→第二刀→第三刀→第五刀→第四刀**，让 SRL 一上线就有完善的晋升路径。

## 八、风险

| 风险 | 概率 | 影响 | 应对 |
|:----|:----:|:----:|:------|
| 跨章节频率继承后直接晋升 | 低 | 本该在当前章验证的角色直接转正 | `_frequency` 继承是合理的——角色在上章已出现 2 次，这章出现 1 次即达标，说明它不是一次性角色 |
| 阈值过低（=1） | 低 | 等同于直接写 SQLite | 阈值设默认为 3 |
| 阈值过高（>10） | 低 | 临时角色难以晋升 | 可在 config.py 中调低 |
| 内存膨胀 | 低 | 每章临时角色数 < 20 | 章节结束时 cleanup 清理 |
| 候选池遗漏临时角色 | 低 | 临时角色无法被匹配 | `get_all_character_names()` 合并正式+临时 |
