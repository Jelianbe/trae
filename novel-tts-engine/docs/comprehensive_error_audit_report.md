### 1.5 错误模式深度分析

#### 模式 A：角色粘性（32 条错误，62.7%）
**现象**：一旦某个角色被匹配成功，后续多条对话持续匹配该角色，即使旁白明确提示说话人已切换。

**典型案例**：
- 索引 04-07：吴工程师被匹配后，连续 4 条赵总监/李经理的台词都错误匹配为吴工程师
- 索引 73-79：刘秘书被动作主语匹配后，连续 7 条错误
- 索引 47-60：张总被匹配后，连续 14 条对话中 11 条错误

**根因**：
1. `_extract_context_speakers()` 的候选池太窄，通常只有 1 个候选
2. 近因衰减只降低当前候选的置信度，但不提供新候选
3. `match_speaker()` 直接取 `context_candidates[0]`，没有其他候选可以切换

#### 模式 B：旁白角色覆盖失效（12 条错误，23.5%）
**现象**：旁白中出现新角色名，但未被正确提取为候选人。

**典型案例**：
- 索引 32：旁白提到"李经理"，但匹配到赵总监
- 索引 62/64/68：旁白场景切换后，候选池未更新

#### 模式 C：对话切换识别失败（7 条错误，13.7%）
**现象**：明显的对话交替（如问答）未能识别说话人切换。

**典型案例**：
- 索引 88：旁白"主要是服务器采购那块"明显是李经理回答，但匹配到赵总监

## 第二部分：架构问题分析

### 2.1 紧耦合架构（Critical）

#### 问题 A-1：speaker_matcher.py 上帝文件
- **文件规模**：1800+ 行
- **职责数量**：7 个独立职责
  1. 角色匹配（core）
  2. 代词消解（内联了 speech_verb_detector）
  3. 称呼推理（内联了 speaker_hint_matcher）
  4. 语义排序（内联了 character_name_validator）
  5. 角色创建（内联了 self_reference_inferrer）
  6. 引号过滤
  7. 活动度追踪
- **影响**：修改一个功能可能影响其他 6 个功能，测试困难

#### 问题 A-2：猴子补丁（Monkey Patching）
- **位置**：pipeline_runner.py 或初始化代码中
- **问题**：动态替换模块方法，破坏封装性
- **影响**：IDE 无法追踪调用链，调试困难

#### 问题 A-3：重复类型定义
- **位置**：pipeline_runner.py 重复定义了 types.py 中的类型
  - `ProgressInfo`
  - `FragmentData`
  - `SentenceData`
  - `ChapterResult`
- **影响**：类型不一致可能导致运行时错误，维护两份定义

### 2.2 候选池窄化问题（Critical - 准确率瓶颈）

#### 问题 B-1：候选池构建逻辑缺陷
**当前流程**：
```
context_before 代词消解 → 描述性角色提取 → 自称推理 → context_after 描述性角色 → 角色库匹配
```

**问题**：
1. **串行而非并行**：每个阶段可能提前返回，导致后续阶段不执行
2. **临时角色过滤过严**：`require_library=True` 过滤掉所有非角色库角色
3. **上下文窗口固定**：只看 `context_before`，不看全文场景变化
4. **无场景切换检测**：当旁白描述新场景时，候选池不重置

**数据支撑**：51 条错误中 32 条（62.7%）是角色粘性错误，根本原因是候选池太窄

#### 问题 B-2：近因衰减设计缺陷
**当前设计**：
```python
if rank == 5:   decay = -0.15  # 最近发言人
elif rank == 4: decay = -0.10  # 第二近
else:           decay = -0.05  # 其他
```

**问题**：
1. **衰减是单向的**：只降低置信度，不提供新候选
2. **衰减值固定**：不考虑对话类型（问答 vs 独白 vs 多人讨论）
3. **窗口大小固定**：只看最近 5 个发言人，不考虑实际对话人数
4. **r3 是甜蜜点**：数据显示 r3 正确率最低（24.1%），说明衰减 -0.05 恰好在错误区间

**改进方向**：衰减应作为**排序调整**而非**置信度惩罚**，且需要足够宽的候选池

### 2.3 状态管理混乱（High）

#### 问题 C-1：三个独立状态系统
| 状态系统 | 数据结构 | 更新时机 | 衰减方式 |
|---------|---------|---------|---------|
| `_recent_speakers` | List[str] | 每次匹配成功 | 固定窗口（最近 5） |
| `_character_activity` | Dict[id, Dict] | 每次匹配成功 | 指数衰减（lambda=0.05） |
| `_recent_mentions` | 未明确 | 提及角色时 | 未明确 |

**问题**：
1. 三个状态系统互相独立，没有统一协调
2. `_recent_speakers` 是字符串列表，无法关联到角色 ID
3. `_character_activity` 使用角色 ID，但候选池使用角色名
4. 状态更新在 `match_speaker()` 末尾，但候选提取在开头，时序不一致

#### 问题 C-2：单例模式全局状态
- **问题**：SpeakerMatcher 使用全局单例，测试间状态不隔离
- **影响**：数据库污染问题（已通过 clean_test_db.py 解决，但架构问题仍在）

### 2.4 错误处理缺失（Medium）

#### 问题 D-1：bare except + pass
- **位置**：多处异常处理使用 `except: pass`
- **影响**：错误被静默吞掉，无法追踪问题根因
- **统计**：代码库中至少 5 处 bare except

#### 问题 D-2：无详细错误上下文
- **问题**：匹配失败时只返回 "unknown"，没有记录：
  - 候选池内容
  - 各阶段得分
  - 衰减后的置信度
  - 为什么选择了某个候选

### 2.5 性能瓶颈（Medium）

#### 问题 E-1：N+1 数据库查询
- **位置**：`get_all_characters()` 每次都是 DB 查询
- **影响**：每句对话都查询数据库，无内存缓存
- **优化空间**：引入角色库缓存，减少 90%+ DB 查询

#### 问题 E-2：线性搜索
- **位置**：`dialogue_map` 使用线性搜索
- **影响**：O(n) 复杂度，长文本中性能下降

#### 问题 E-3：重复初始化
- **位置**：每句调用 `get_emotion_extractor()`
- **影响**：每次重新初始化情感提取器

### 2.6 数据一致性问题（Medium）

#### 问题 F-1：两套 SentenceData 定义
- **位置**：types.py 和 pipeline_runner.py 各定义一套
- **影响**：类型不一致可能导致字段缺失或类型错误

#### 问题 F-2：MatchResult 来源不同
- **问题**：不同匹配阶段返回的 MatchResult 结构不同
- **影响**：下游处理需要兼容多种格式

### 2.7 硬编码管理（Low）

#### 问题 G-1：ROLE_CORE_WORDS 重复定义
- **位置**：descriptive_role_extractor.py 和 speaker_matcher.py
- **影响**：修改一处需要同步修改另一处

| 优先级 | 任务 | 预期效果 | 工作量 | 风险 |
|-------|------|---------|--------|------|
| **P0** | 扩大候选池宽度 | +20~30% | 中 | 低 |
| **P0** | 重构近因衰减为排序调整 | +10~15% | 低 | 低 |
| **P1** | 引入场景切换检测 | +5~8% | 中 | 中 |

### 4.2 详细改进方案

#### P0-1：扩大候选池宽度（核心优化）

**问题**：当前候选池通常只有 1-2 个候选，衰减后无法切换。

**方案**：
1. **并行候选提取**：将所有候选提取阶段改为并行执行，收集所有候选后再排序
2. **放宽角色库过滤**：`require_library=False`，允许临时角色进入候选池
3. **增加上下文窗口**：从固定 `context_before` 改为动态窗口，检测场景切换
4. **添加对话模式识别**：识别问答、独白、多人讨论等模式，调整候选策略

**验证标准**：
- 候选池平均宽度从 1.2 提升至 3.0+
- r3 衰减正确率从 24.1% 提升至 60%+

#### P0-2：重构近因衰减机制

**问题**：当前衰减是置信度惩罚，适得其反。

**方案**：
1. **改为排序调整**：衰减不改变置信度，只调整排序权重
2. **动态衰减值**：根据对话模式调整衰减强度
   - 问答模式：高衰减（-0.20）
   - 独白模式：低衰减（-0.05）
   - 多人讨论：中衰减（-0.10）
3. **扩大衰减窗口**：从固定 5 人改为动态窗口（实际对话人数）

**验证标准**：
- 衰减后对话正确率 > 无衰减对话正确率
- r3/r4/r5 各级正确率差异 < 15%

#### P1-1：引入场景切换检测

**问题**：旁白描述新场景时，候选池不更新。

**方案**：
1. **场景关键词检测**：识别场景切换关键词（如"办公室"、"会议室"、"回到家"）
2. **角色出场检测**：旁白中首次出现的角色名作为高优先级候选
3. **场景-角色映射**：维护场景到角色的映射表

#### P1-2：拆分 speaker_matcher.py

**方案**：
1. **恢复 5 个独立模块**：
   - `speech_verb_detector.py`
   - `speaker_hint_matcher.py`
   - `character_name_validator.py`
   - `self_reference_inferrer.py`
   - `action_subject_extractor.py`
2. **定义清晰接口**：每个模块提供统一的 `extract()` 接口
3. **管道式调用**：SpeakerMatcher 作为编排器，调用各模块

#### P2-1：角色库内存缓存

**方案**：
1. **启动时加载**：应用启动时将角色库加载到内存
2. **变更时更新**：角色增删改时更新缓存
3. **缓存失效策略**：设置 TTL 或手动刷新

#### P2-2：统一类型定义

**方案**：
1. **删除 pipeline_runner.py 中的重复定义**
2. **统一使用 types.py 中的定义**
3. **添加类型检查 CI**

## 第六部分：结论与下一步行动

### 6.1 核心结论

1. **长文本 40% 正确率的根本原因是候选池窄化**：51 条错误中 32 条（62.7%）是由于候选池只有 1-2 个候选，衰减后无法切换到正确角色。

2. **近因衰减设计适得其反**：衰减本应提升准确率，但实际衰减后的对话正确率普遍低于无衰减（r3 仅 24.1% vs 无衰减 77.8%）。

3. **架构问题加剧了准确率问题**：紧耦合、状态混乱、错误处理缺失使得问题难以定位和修复。

4. **理论改善空间巨大**：解决候选池和衰减问题后，长文本准确率可从 40% 提升至 75~80%。

### 6.2 下一步行动

1. **立即执行（P0）**：
   - 扩大候选池宽度（并行提取 + 放宽过滤）
   - 重构近因衰减为排序调整

2. **短期执行（P1）**：
   - 引入场景切换检测
   - 拆分 speaker_matcher.py

3. **中期执行（P2-P3）**：
   - 角色库内存缓存
   - 统一类型定义
