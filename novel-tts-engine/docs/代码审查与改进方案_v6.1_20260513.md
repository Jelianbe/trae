### 原则2：不确定时返回"未知"，不做硬猜测

**评级：✅ 主流程合规，⚠️ 存在2个边角风险点**

#### 2.2.1 主流程合规确认

- `_extract_context_speakers` 无候选时返回 `('未知_无法推断', '无上下文线索', 0.30)` ✅
- `match_speaker` 中跳过以 `未知_` 开头的候选 ✅

#### 2.2.2 风险点1：Fallback链可能在信息不足时猜测

`match_speaker` 方法（[speaker_matcher.py:L899-L973](file:///d:/trae/novel-tts-engine/pipeline/speaker_matcher.py#L899-L973)）在上下文推理无结果后，继续触发以下 fallback：

1. **semantic matching**（L960-L963）：用 sentence-BERT 找最相似角色，置信度 0.6~0.8
2. **trigger words**（L965-L967）：头衔触发词匹配
3. **address inference**（L969-L971）：称呼推断

当"无任何线索"时，这些 fallback 本质上是在"猜"。仅在前面有正向信号时触发才合理。

#### 2.2.3 风险点2：临时角色创建门槛过低

`_register_temporary_character`（[speaker_matcher.py:L234-L257](file:///d:/trae/novel-tts-engine/pipeline/speaker_matcher.py#L234-L257)）：只要 `_has_speech_context` 返回 True（或 `skip_speech_check=True`），任何候选都会被创建为角色并持久化到 SQLite。这会导致角色库被低频噪声实体污染。

## 四、算法漏洞与系统性缺口分析

### 4.1 架构级缺口

#### 缺口1：对话检测完全依赖引号

**位置**：[speaker_hint_matcher.py:L35-L60](file:///d:/trae/novel-tts-engine/pipeline/speaker_hint_matcher.py#L35-L60) `DIALOGUE_PATTERNS`

**现象**：只有被引号包围的文本才被识别为对话。以下格式完全被忽略：
- 冒号直接引语：`林轩：来一间上房。`
- 换行分段对话（微信对话体）
- 部分网文使用 `——` 破折号引导对话

**影响**：只要 `DIALOGUE_PATTERNS` 没匹配到引号，整个段落的说话人识别完全失效。

#### 缺口2：上下文窗口过窄且跨段落割裂

**位置**：[speaker_matcher.py:L1116-L1119](file:///d:/trae/novel-tts-engine/pipeline/speaker_matcher.py#L1116-L1119) 和 [L1105](file:///d:/trae/novel-tts-engine/pipeline/speaker_matcher.py#L1105)

**现象**：
- 上文窗口 = 上一个引号结束到当前引号开始（可能极短）
- 下文窗口 = 当前引号结束到下一个引号开始
- `analyze_dialogue` 在开头清空 `_recent_speakers`
- 评估脚本在每个段落间 `reset_activity`

**影响**：系统无法利用跨句子的角色活跃度来辅助判断。

#### 缺口3：无角色消歧机制

**现象**：
- 同一描述性称呼在不同章节指不同角色（如两个"黑衣人"）
- 单字名在全文中有多个同名者
- "老者"在第一章是"药老"，在第五章是另一个老者

**影响**：所有同名实体被合并为同一角色，导致角色对话归属错误。

#### 缺口4：角色库无频率机制

详见原则6审查。

#### 缺口5：评估行为与生产环境不一致

**位置**：[evaluate_v6_improvements.py:L54-L55](file:///d:/trae/novel-tts-engine/analysis_reports/评估脚本/evaluate_v6_improvements.py#L54-L55)

**现象**：每个测试段落独立调用 `analyze_dialogue` + `reset_activity`，但生产环境中 `pipeline_runner._process_chapter` 是整章连续调用。

**影响**：评估结果可能高估或低估真实场景的准确率。

### 4.2 算法细节漏洞

#### 漏洞1：步骤3对 context_after 的不合理跳过

**位置**：[speaker_matcher.py:L532-L533](file:///d:/trae/novel-tts-engine/pipeline/speaker_matcher.py#L532-L533)

```python
if ctx_label == '后':
    continue
```

**问题**：步骤3（角色库直接匹配）在处理 context_after 时，只做了"声音指示"匹配后就跳过了说话动词、冒号主语等后续规则。后文中的 `"...",林轩说道` 模式对角色库角色无效。虽然步骤6通过 NER 重新处理了 context_after，但 NER 路径可能不如角色库路径准确。

**建议修复**：对于 context_after，仅跳过"冒号主语"规则（因为后文中的 `XX：` 更可能是新对话），保留其他规则的检查。

#### 漏洞2：`MODIFIER_PATTERN` 包含危险通配

**位置**：[descriptive_role_extractor.py:L80-L92](file:///d:/trae/novel-tts-engine/pipeline/descriptive_role_extractor.py#L80-L92)

```python
r'[^\s，。！？\n「」『』""]{1,6}'  # 匹配任何非标点字符
```

**问题**：这个分支会匹配任何 1~6 个中文字符，导致大量误匹配：
- `推开门` + `骑士` → `"推开门骑士"` 被提取
- `轻轻放` + `修士` → `"轻轻放修士"` 被提取

#### 漏洞3：`_is_clean_per_entity` 缺少"的"字结构检测

**位置**：[entity_cleaner.py:L201-L210](file:///d:/trae/novel-tts-engine/pipeline/entity_cleaner.py#L201-L210)

**问题**：当前修饰词模式无法过滤：
- `面目慈祥的老者`
- `手持长剑的骑士`
- `从暗处走出的身影`

中文中 `XX的YY` 结构几乎不可能是纯人名（除非 `XX` 是人名修饰语）。

#### 漏洞4：`character_name_validator.is_valid` 的姓氏要求过于严格

**位置**：[character_name_validator.py:L52-L69](file:///d:/trae/novel-tts-engine/pipeline/character_name_validator.py#L52-L69)

```python
if len(name) >= 2 and name[0] in SINGLE_CHAR_SURNAMES:
    return True
```

**问题**：网文中代号式名字如"暗刃"、"血手"、"影杀"的首字不在姓氏表中会被拒绝，但它们确实是有效的网文角色名。

#### 漏洞5：自称推断失败时产生噪音

**位置**：[self_reference_inferrer.py:L72-L77](file:///d:/trae/novel-tts-engine/pipeline/self_reference_inferrer.py#L72-L77)

**问题**：当无法将自称词映射到角色时，返回 `('未知', '自称词:X', 0.40)`。虽然当前 `match_speaker` 会跳过这个候选，但这依赖隐式约定。

## 五、改进方案设计

### 5.1 三阶段推进策略

```
P0（立即执行） → P1（近期执行） → P2（架构重构）
   0天影响准确率      预计+1~3%准确率      突破74%目标
```

### 5.2 P0：消除代码层面的违规和重复（含原则违反修复）

| 编号 | 改进项 | 影响模块 | 风险 |
|------|--------|---------|------|
| P0-1 | **创建 `speech_verb_detector.py` 统一说话动词检测** | 新建 + 8个模块引用改造 | 低 — 语义等价替换 |
| P0-2 | **将 nlp_basics._enhance_entities 迁移到 entity_cleaner** | `nlp_basics.py`, `entity_cleaner.py` | 中 — 需跑回归 |
| P0-3 | **消除 ROLE_CORE_WORDS 双重维护** | `speaker_matcher.py`, `descriptive_role_extractor.py` | 低 — 只改 import |

**P0-1 详细设计 — `speech_verb_detector.py`：**

```python
# pipeline/speech_verb_detector.py
"""
说话动词检测器 — 唯一权威源。

用途：所有需要判断"某词是否表示说话"的模块通过此模块获取信息。
来源：中文标点规范 GB/T 15834-2011（引号引导词）+
      现代汉语语法（主谓结构中的言说动词）+
      网文高频说话模式统计
"""

# 纯说话动词（不带修饰）
SIMPLE_SPEECH_VERBS = [
    '道', '说', '问', '喊', '叫', '答', '应',
    '喝', '嚷', '骂', '斥', '吼', '回',
]

# 表情修饰 + 说话（前2字情绪/表情，后1~2字说话动词）
# 模式：情绪词 + 道/说/问
EMOTION_MODIFIED_SPEECH = [
    '笑道', '叹道', '怒道', '喝道', '哼道', '嚷道',
    '骂道', '泣道', '冷冷道', '淡淡道', '沉声道',
    '低声道', '高声道', '厉声道', '轻声道',
    '冷笑道', '怪笑道', '柔声道', '安慰道',
]

# 复合动作 + 说话（动作词 + 道/说/问）
COMPOUND_ACTION_SPEECH = [
    '说道', '问道', '答道', '回答道', '回应道',
    '接道', '续道', '摇头道', '点头道', '叹息道',
    '冷笑道', '讽刺道', '打趣道', '赞叹道',
]

# 说话边界词（角色名后紧跟，用于方向-B反向提取）
SPEECH_BOUNDARY_WORDS = SIMPLE_SPEECH_VERBS + EMOTION_MODIFIED_SPEECH + COMPOUND_ACTION_SPEECH

class SpeechVerbDetector:
    def is_speech_verb(self, word: str) -> bool:
        """判断是否纯说话动词"""
    
    def is_speech_related(self, word: str) -> bool:
        """判断是否说话相关（含表情+复合）"""
    
    def extract_speech_context(self, text: str) -> List[Tuple[str, int]]:
        """从文本中提取所有说话动词位置"""
    
    def get_pattern(self) -> str:
        """获取正则模式字符串，用于拼接到其他正则中"""
```

#### P0-NEW-A 详细设计 — 评估上下文修复

**问题**：GT短用例（如修仙GT 55条对话、西幻GT 68条对话、斗破GT 10条对话）的测试方式是提取每句话单独喂给管道，但HanLP需要上下文才能提取人物实体。

**修复方案**：
- 修改 `merge_gt_tests.py`：提取短用例时保留完整段落上下文
  - 从原文中截取对话前后各 1~2 句作为 context
  - 或者：直接使用整段/整章作为输入，然后逐条匹配结果
- 修改 `test_data_unified.py`：每个用例包含 `full_paragraph`（用于实际评测）和 `dialogues`（用于验证）
- 修改 `evaluate_unified.py`：使用 `full_paragraph` 作为输入，逐条匹配 `dialogues` 期望

#### P0-NEW-B 详细设计 — 对话边界检测增强

**问题**：29条非对话被检测为对话且返回了具体说话人（而非"未知"）。这些是地名/物品名引用、形容词强调、内心独白等被引号包裹的内容，系统不仅检测为对话，还错误地分配了一个说话人。

**典型失败模式**：
- `"断龙崖"` → 说话人="孙项明"（孙项明在附近，但不是说话人）
- `"求稳"` → 说话人="孙项明"
- `"跳，还是不跳？"` → 说话人="林雪"

**策略（合规方案，不使用whitelist）**：

1. **说话动词锚定**（核心）
   - 引号前后 N 个字符内必须存在说话动词（引用 `speech_verb_detector.py`）
   - 距离阈值：前后各 15 个汉字
   - 无锚点 → 不分配说话人（返回"未知"即可，符合原则2）

2. **引号内容结构分析**
   - 引号内是纯名词短语（无谓语动词）→ 不视为对话
   - 引号内是单个字符 + 感叹号（`"轰！"`）→ 抑制
   - 引号内是单个词且无标点（`"求稳"`）→ 抑制
   - 引号内是疑问句/感叹句 → 保留（可能是独白式对话）

3. **引用标记 pattern 抑制**
   - `"…"…记载/刻/铭文/卷轴/玉简/书` → 抑制（文献引用）
   - `"…"…写道/记下` → 抑制（书中书）

**预期**：non_dialogue 类 FP 从 29 降至 ≤ 5（返回具体人的情况）

#### P1-NEW 详细设计 — 说话人匹配逻辑优化

**问题**：38条对话正确检测到但说话人选错。

**典型失败模式**：
- `"把东西交出来。"` → 期望="黑衣人" 实际="苏夜"（附近有两人，选错了）
- `"这枚丹药，你先服下。"` → 期望="药老" 实际="萧炎"
- `"郭道友。"` → 期望="孙项明" 实际="郭垣"（被呼语误导）

**修复方向**：
- 说话动词绑定：`"X怒道"` 明确绑定 X 为说话人
- 呼语排除：`"X，你好"` 中 X 是听话人，不是说话人（N-1 已规划）
- 动作紧邻关联：`"X冷笑着"` 绑定 X 为说话人（N-2 已规划）
