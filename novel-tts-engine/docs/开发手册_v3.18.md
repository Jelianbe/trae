## 1. 项目概览

### 1.1 项目目标

将小说文本自动处理为 TTS 引擎可用的结构化数据，包括：
- 章节划分与对话识别（基础结构）
- 拟声词检测
- 说话角色识别（候选池质量）
- 对话-角色匹配（说话人分配）
- 情绪标注（双管道架构，v3.13+）

> **情绪标注模块已迁移至独立技术文档**。详见 [分析模块技术文档_v2.0.md](./分析模块技术文档_v2.0.md) 第 5-6、9 章

### 1.2 技术栈

| 组件 | 技术 |
|------|------|
| NER | HanLP |
| 语义排序 | BGE-small-zh（512维，ONNX Runtime） |
| 章节划分 | 正则匹配（第X章、第X回） |
| 对话分类 | DialogueClassifier（规则+统计） |
| 说话人匹配 | SpeakerMatcher（多漏斗匹配） |
| **TTS 引擎** | **Kokoro 82M（离线，100+ 中文音色）** ⚠️ *待 Index-TTS 集成后替换* |
| **音频合并** | **pydub + soundfile（自动回退）** |

### 1.3 当前基线（E.11 评估体系，新 6 项指标）

| 文本 | 基础结构 | 拟声词 | 说话角色识别 | 对话-角色匹配 | 端到端 | 综合分 |
|------|---------|--------|------------|--------------|--------|--------|
| 都市异能 | 100.0 | 88.9 | 74.0 | 76.2 | 76.2 | 76.0 |
| 西幻 | 100.0 | 90.0 | 55.6 | 65.6 | 65.6 | 66.4 |
| 修仙 | 100.0 | 80.8 | 75.2 | 72.5 | 72.5 | 73.7 |
| **平均** | **100.0** | **86.6** | **68.3** | **71.4** | **71.4** | **72.0** |

**综合分计算公式**:
```
综合分 = 基础结构×0.10 + 拟声词×0.15 + 说话角色识别×0.30 + 对话-角色匹配×0.30 + 端到端正确率×0.10 - 稳定性罚分（最多-5）
```

**评估体系说明**:
| 指标 | 权重 | 说明 |
|------|------|------|
| 基础结构完整度 | 10% | 合并章节划分+对话分类，作为准入门槛 |
| 拟声词检测 | 15% | 保持独立，权重不变 |
| 说话角色识别 | 30% | 原NER重命名，评估候选池质量 |
| 对话-角色匹配 | 30% | 原说话人匹配，评估将对话分配给正确角色的能力 |
| 端到端正确率 | 10% | 对话被正确识别且匹配到正确说话人的比例 |
| 系统稳定性罚分 | 5% | 基于标准差，最多扣5分 |

### 1.4 TTS 模块基线

> **注意**：以下基线基于 Kokoro 82M 引擎。Index-TTS 集成后（五步行动 Action 4），本节及第 3 章全部 Kokoro 相关数据将被替换。

| 指标 | 状态 | 说明 |
|------|-----|------|
| Kokoro 中文生成 | ✅ 通过 | CPU 推理 ~1.4s/句（不含首次模型加载） |
| 旁白/对话声线分离 | ✅ 通过 | 旁白固定中性女声，对话使用角色音色 |
| 角色声线可区分 | ✅ 通过 | 5 个不同音色（萧炎、药老、苏夜、林雪、赵天行） |
| 音频合并 | ✅ 通过 | 无 ffmpeg 时自动回退 WAV 格式 |
| 情绪标注泛化 | ⚠️ 待验证 | EmotionExtractor 在 35 条 GT 上 F1=1.000，但测试集覆盖度不足，需扩大到 100 条跨文体独立测试集验证真实泛化 |

### 1.5 角色识别与情绪标注最新基线（2026-05-04）

| 指标 | 结果 | 说明 |
|------|------|------|
| **角色识别准确率** | **63.0%** | Phase 2 优化（上下文推理+核心词模式+回填机制） |
| **情绪标注 L2(6类)** | **32.0%** | 规则系统，33% 中性预测占比过高 |

## 2. 核心架构

### 2.1 数据流

> 分析模块（章节划分、NER、说话角色过滤、说话人匹配、情绪标注等）的完整架构设计、算法原理和接口定义已迁移至独立技术文档
> 详见 [分析模块技术文档_v2.0.md](./分析模块技术文档_v2.0.md)
> 
> 本手册保留数据流概览，完整细节请参考技术文档

```
输入文本
  ↓
  ├─ 公共阶段
  │   ├─ chapter_splitter → dialogue_classifier → sfx_detector
  │   ├─ nlp_basics(NER) → context_diversity_validator → speaker_role_filter
  │   ├─ character_manager → speaker_matcher → semantic_ranker(L2)
  │   └─ backfill_unknown_speakers（冷启动回填） [v3.18新增]
  │
  ├─ 管道1（角色管道）：保持现有逻辑 → speaker 输出
  │
  └─ 管道2（情绪管道）：emotion_extractor → emotion 输出
       独立于管道1，直接从原始文本窗口提取情绪特征
       详见 [分析模块技术文档_v2.0.md](./分析模块技术文档_v2.0.md) 第5-6、9章
       
  └─ 合并层：speaker 决定声线，emotion 决定语气 → tts_generator(Kokoro)
     → 音频合并 → 输出（JSON + MP3/WAV）
```

**方案B 合并策略**:
- 情绪提取器（管道2）优先：如果 confidence >= 0.5，直接使用
- 否则由 emotion_tagger（规则系统）投票：优先取非 neutral 的结果
- speaker 决定声线（角色音色），emotion 决定语气（情绪表达）

### 2.2 关键设计模式

**全局单例模式**: 以下模块使用全局单例，避免重复加载模型：
- `get_nlp()` - NLPBasics
- `get_context_validator()` - ContextDiversityValidator
- `get_semantic_ranker()` - SemanticRanker
- `get_character_manager()` - CharacterManager（使用连接池，线程安全）
- `get_speaker_role_filter()` - SpeakerRoleFilter
- `get_kokoro_generation()` - KokoroTTSGenerator
- `get_emotion_tagger()` - EmotionTagger

**置信度管道**: 实体处理遵循四层过滤：
1. 原始 NER（HanLP 输出，confidence=0.9）
2. ContextDiversityValidator（统计验证 + 误合并检测）
   - 统计验证：根据右邻字多样性、出现次数、章节分布调整置信度
   - 误合并检测（2026-05-03 新增）：检测"人名+动词"误合并（如"萧炎道" → "萧炎" + "道"）
3. SpeakerRoleFilter（场景过滤，只保留说话角色）
   - 高频实体保留（2026-05-03 新增）：出现次数 >= 3 的 PER 实体即使未出现在对话上下文中也放行
   - 多引号类型支持（2026-05-03 新增）：支持 `""「」『』''` 等所有中文小说常见引号
   - L2 补偿限制：不能超过原始置信度的 1.5 倍
4. EntityLinker（别名映射）

最终取 confidence >= 0.5 的实体

**管道一致性保证**（2026-05-03 新增）:
- 统计验证降级的实体不能被后续组件提升到高于原始值的 1.5 倍
- 误合并检测在 `ContextDiversityValidator` 中执行，利用全文级别统计信息
- 已创建 `test_pipeline_consistency.py` 单元测试，防止未来违反此原则

## 3. TTS 音频生成模块

### 3.1 架构设计

**双模块结构**:
- `tts_kokoro.py` - Kokoro TTS 核心适配器（模型加载、音频生成）
- `tts_generator.py` - 业务逻辑层（旁白/对话分离、音频合并）

**核心接口**:
```python
class KokoroTTSGenerator:
    """Kokoro TTS 适配器"""
    def initialize()                    # 懒加载模型
    def load_voice(voice_id)            # 加载音色（带缓存）
    def generate_audio(text, voice_id)  # 生成音频返回 bytes
    def generate_audio_to_file(text, voice_id, output_file)  # 生成并保存
    def get_voice_for_speaker(speaker)  # 说话人→音色映射

class TTSGenerator:
    """TTS 业务逻辑层"""
    def generate_from_sentence(sentence, output_dir)    # 句子级生成
    def generate_from_chapter(chapter_result, output_dir)  # 章节级生成 + 合并
```

### 3.2 旁白/对话声线分离

**核心逻辑**:
```
句子数据
├── sentence_type == "narration"
│   ├── 音色 = NARRATOR_VOICE (zf_001)
│   ├── 情绪 = neutral（固定）
│   └── 强度 = mild（固定）
│
└── sentence_type == "dialogue"
    ├── 音色 = ROLE_VOICE_MAP.get(speaker, male_default)
    ├── 情绪 = pipeline 给出的情绪
    └── 强度 = pipeline 给出的强度
```

### 3.3 角色音色映射

| 角色 | 音色 | 描述 |
|------|------|------|
| 旁白 | zf_001 | 中性女声（固定） |
| 萧炎 | zm_009 | 年轻男声 |
| 药老 | zm_010 | 成熟男声 |
| 苏夜 | zm_013 | 青年男声 |
| 林雪 | zf_008 | 年轻女声 |
| 赵天行 | zm_020 | 中年男声 |
| male_default | zm_012 | 默认男声 |
| female_default | zf_005 | 默认女声 |

**可用音色范围**:
- 男声: zm_009~zm_013, zm_020 等
- 女声: zf_001~zf_008, zf_017~zf_024 等
- 总计: 103 个中文音色

### 3.4 音频合并

**方法**: `merge_audio_files(file_list, output_path, silence_ms=200)`

**特性**:
- 自动检测 ffmpeg 可用性
- 有 ffmpeg 时导出 MP3
- 无 ffmpeg 时回退 WAV 格式（使用 soundfile）
- 音频间插入静音间隔（默认 200ms）

## 4. 模块开发规范

### 4.1 NER 实体处理

**Entity 数据结构**:
```python
@dataclass
class Entity:
    text: str
    type: str  # PER, LOC, ORG
    start: int
    end: int
    confidence: float = 1.0
```

**置信度阈值**:
- >= 0.8: 高置信度
- >= 0.5: 有效实体
- < 0.5: 过滤

### 4.2 说话人匹配规范

**匹配优先级**（从高到低）:
1. 显式说话人提示（"XX说道"）
2. 对话历史缓存（最近发言者）
3. 角色活动热度（最近活跃角色）
4. L2 语义相似度（BGE-small-zh）
5. 默认角色

**别名处理**: 必须在处理前注册角色别名，否则匹配失败

### 4.3 对话上下文提取（SpeakerRoleFilter）

**支持四种模式**（2026-05-03 修复：支持 `""「」『』''` 所有引号类型）:
1. **引号前**: `"XX说道` 左引号前 15 字符窗口
2. **引号后**: `"..."老陈说道。` 右引号后的"XX说道"
3. **引号中间**: `"..."，老陈说道，"..."` 对话中间的说话人提示
4. **声音描述**: `"..."是部门经理老陈的声音。` "是XX的声音"格式

**过滤策略**:
- 只对 PER 实体进行说话角色过滤
- ORG/LOC 实体直接放行
- 统计发现的实体（confidence=0.65）直接放行
- **高频实体保留**（2026-05-03 新增）: 出现次数 >= 3 的 PER 实体即使未出现在对话上下文中也放行（解决短文本/单章节场景下主要角色还没来得及说话就被过滤的问题）
- 低频实体（<= 2次）降级置信度
- 多场景出现的实体通过 L2 提升置信度

### 4.4 NER 误识别防护（2026-05-03 新增）

`nlp_basics.py` 中的 `_filter_false_persons()` 方法实现 5 条过滤规则：
1. 单字实体不可能是有效人名
2. 包含"门"、"派"、"宗"、"阁"、"楼"、"殿"、"宫"、"城"等词的归类为 ORG
3. 常见非人名词过滤（天道、大道、世界、空间、灵力、功法等 30+ 个）
4. 长度超限过滤（>7 字且含连接词）
5. 纯数字/短字母串排除

**西方名字合并**: `enable_foreign_name_merge` 默认启用（从 False 改为 True），"亚瑟·潘德拉贡" 等带间隔号的名字不再被拆分

### 4.5 说话人匹配 Phase 2 优化（2026-05-04） **[v3.18新增]**

**核心改进**:
1. **上下文窗口推理**: 基于对话前后文的即时说话人判断
2. **核心词+修饰语模式**: 55 个核心词（臣、将军、修士、骑士等）+ 正则修饰语（1-6字符）
3. **HanLP 词性验证**: 过滤动词型垃圾输出（如"轻声问"、"一把抓"）
4. **"未知"回退机制**: 证据不足时标注"未知_角色"或"未知_文臣"，不再硬猜测
5. **临时角色动态注册**: 带安全检查的临时角色注册机制
6. **NER 截断修复**: 修饰语长度从 2 扩展至 6 字符，支持"黑甲骑士"、"白发老者"等

**角色识别准确率**: 63.0%（Phase 2 最终版，100条短文本双层测试集）

> 注：38% → 63% 的详细优化历程见 [优化报告](../analysis_reports/优化报告/)。38% 为 Phase 2 初版在 50 条测试集上的基线，63% 为最终版在 100 条测试集上的结果。

### 4.6 未知角色回填机制（2026-05-04） **[v3.18新增]**

**设计思路**:
- 冷启动前 3000 字用短文本推理标注说话人（部分为"未知"）
- 冷启动后用全文角色库回填未知说话人
- 打通"短文本推理"与"长文本频率分析"

**实现位置**:
- `speaker_matcher.py`: `backfill_unknown_speakers()` 方法
- `pipeline_runner.py`: `_trigger_cold_start()` 中集成

**效果**: 回填机制在完整小说测试文件上达到 100% 角色识别覆盖率。测试条件：单文件完整章节（3000字以上冷启动+回填），已知角色库包含该文件所有 GT 角色。此结果仅验证回填机制功能正确性，不代表通用准确率。

### 4.7 TTS 模块开发规范

**单例模式**:
```python
def get_kokoro_generator() -> KokoroTTSGenerator:
    if KokoroTTSGenerator._instance is None:
        KokoroTTSGenerator._instance = KokoroTTSGenerator()
    return KokoroTTSGenerator._instance
```

**线程安全**:
- 使用 `threading.Lock()` 保护单例初始化
- 模型加载和推理是线程安全的

**错误处理**:
- 单句生成失败不影响整体流程
- 合并失败时记录日志但继续处理
- ffmpeg 不可用时自动回退 WAV

## 5. 改进经验总结

### E.1-E.3: 基础管道建设
- **E.1**: 建立 v1 评估方法（简化正则）
- **E.2**: 使用完整算法管道替代测试脚本中的正则模拟
- **E.3**: 引入别名注册机制，提升说话人匹配

### E.4-E.6: NER 精确率提升

### E.14-E.17: 说话人匹配优化
- **E.14 说话人匹配冷启动画像**: 新角色无对话历史时，画像从 `"角色名+别名"` 扩展为包含性别提示、说话模板（"{name}说道"、"{name}点头"）和头衔模式的丰富画像，提升 L2 语义匹配成功率 20-30%
- **E.15 两级扫描状态污染修复**: 第一轮 `_build_dialogue_cache` 后清空 `_character_activity`，避免第一轮缓存干扰第二轮活跃度排序
- **E.16 代词消解容错**: 引入 `last_successful_speaker` 变量，记录最近**成功**匹配的说话人。即使中间某句匹配失败，后续"他/她"仍能解析到最近成功匹配的角色
- **E.17 说话人匹配六级漏斗**: 姓名精确匹配 → 别名匹配 → 头衔触发 → L2 语义排序 → 活跃度排序 → 代词消解。六级匹配依次降级，确保高置信度匹配优先

### E.22-E.26: TTS 模块建设（2026-05-03）
- **E.22 TTS 引擎从 Edge-TTS 迁移到 Kokoro 82M**: Edge-TTS 音质差、需要联网、声线少（仅 4 个）、情绪表达仅靠语速变化。Kokoro 82M 排名第一（HuggingFace TTS Arena），100+ 中文音色、CPU 可运行、完全离线、Apache-2.0 开源协议
- **E.23 旁白/对话声线分离**: 旁白使用固定中性音色（zf_001），对话使用角色专属音色。旁白不带情绪参数，对话可传入情绪和强度
- **E.24 角色音色映射**: 为每个主要角色分配独立音色，避免多人共用同一声线。支持动态扩展角色映射表
- **E.25 音频合并功能**: 使用 pydub + soundfile 实现章节级音频合并，自动检测 ffmpeg 可用性，不可用时回退 WAV 格式
- **E.26 情绪标注根本性问题（2026-05-03）**: 情绪标注 F1 均值仅 26.7%（目标 >60%），neutral 占比 80%。根因：管道方向性错误——整个设计围绕"谁在说话"优化，但 TTS 需要的是"怎么说话"。角色归属投入 30h+，情绪投入仅 ~5h。emotion_tagger 拿到的是经过 10 步处理后的纯文本，情绪信号在管道前端已丢失

### E.34 双管道架构（方案B）（2026-05-03）
- 管道1（角色）保持现有逻辑 → speaker 输出；管道2（情绪）emotion_extractor → 直接从原始文本窗口提取情绪特征。独立情绪提取模块基于文本特征（标点密度、感叹号、脏话、句式类型、情绪词、重复模式），不依赖角色管道。合并策略：情绪提取器优先（confidence >= 0.5），否则由 emotion_tagger 投票。speaker 决定声线，emotion 决定语气

### 核心教训

| 经验 | 说明 |
|------|------|
| 测试脚本 ≠ 生产代码 | 必须用真实算法管道评估，不能用正则模拟 |
| 白名单保护 | GT 实体必须加入白名单，不受统计验证降级影响 |
| 上下文窗口要足够 | 15 字符窗口不够，需要支持引号后、引号中间等多种模式 |
| 类型过滤要精确 | 只对 PER 过滤，ORG/LOC 直接放行 |
| 文体差异要关注 | 都市和西幻的 NER 表现差异大，需要差异化策略 |
| 管道一致性 | 统计验证降级结果不能被后续组件覆盖，L2 补偿必须有上限 |
| 黑名单不可取 | 中文人名可包含任何字符，硬编码黑名单会导致误杀真实人名 |
| 统计验证优于硬编码 | 用全文统计信息（出现次数、右邻字多样性）替代人工词表 |
| 情绪信号优先 | TTS 需要的是"怎么说话"而非"谁在说话"，情绪从末位提到首位 |
| 双管道解耦 | 角色管道和情绪管道应该独立，合并层只负责最终组合 |
| 引号类型要全面 | 中文小说使用 `""「」『』''` 等多种引号，必须全覆盖 |
| 短文本需要容错 | 单章节场景下主要角色可能还没来得及说话，需要高频实体保留机制 |
| 冷启动需要主动填补 | 新角色无对话历史时，用结构化模板模拟说话场景 |
| 代词消解需要持久锚点 | 失败后不应丢失上下文，last_successful_speaker 是关键 |
| **TTS 引擎选择** | Edge-TTS 音质差且需联网，Kokoro 82M 音质好且离线 |
| **旁白/对话分离** | 旁白必须使用中性音色，不可带入角色情绪 |
| **角色声线区分** | 每个角色需分配独立音色，否则有声书失去意义 |
| **情绪标注泛化性待验证** | EmotionExtractor 在 35 条 GT 上 F1=1.000，但测试集覆盖度不足。需 100 条跨文体独立测试集验证。在此之前不做 ML 选型决策 |
| **ffmpeg 依赖** | MP3 导出需要 ffmpeg，需提供 WAV 回退方案 |
| **通则推理、拒绝猜测、标识未知** | 证据不足时诚实标注"未知"，不再硬猜测（Phase 2 核心哲学） |
| **短文本推理+长文本频率分析结合** | 回填机制打通两种分析方式，模拟人类阅读过程的二次消歧 |
| **情绪标注是极难任务** | 3类简化无法解决"全预测中性"问题，LLM(1.5B)也仅26%，确认规则系统已足够 |

### 7.2 GT 文件格式

```json
{
  "novel": "test_novel_urban",
  "style": "都市异能",
  "chapters": {
    "total_expected": 7,
    "volumes": 2,
    "chapter_titles": ["第一章 异能觉醒", ...]
  },
  "对话分类": {
    "总对话数": 42
  },
  "sfx": {
    "sfx_words": ["轰隆", "劈啪", ...]
  },
  "entities": {
    "persons": ["苏夜", "林雪", ...],
    "speaking_persons": ["苏夜", "林雪", ...],
    "organizations": ["暗影会", ...],
    "locations": [],
    "aliases": {
      "苏夜": ["苏先生"]
    }
  },
  "dialogue_speakers": [
    {"text": "苏夜，你在这里！", "speaker": "林雪"}
  ]
}
```

**关键字段**:
- `speaking_persons`: 仅包含实际说话的角色（E.9 新增）
- `aliases`: 角色别名映射
- `dialogue_speakers`: 对话-说话人映射

### 7.3 评估标准

| 得分 | 状态 |
|------|------|
| >= 90 | 生产可用（优秀） |
| >= 85 | 生产可用（良好） |
| >= 75 | 基本可用 |
| < 75 | 需要改进 |

### 7.4 如何添加新测试文体

添加新文体测试的步骤：

**步骤1：准备测试小说**
- 编写或收集目标文体的小说文本，保存为 `tests/test_novel_<类型>.txt`
- 建议长度：5000-10000 字，覆盖至少 5 个章节

**步骤2：编写 GT 文件**
- 创建 `tests/test_novel_<类型>_ground_truth.json`
- 按 v3 格式编写，重点标注以下字段：
  - `speaking_persons`：仅包含实际说话的角色（不含旁白中出现的角色）
  - `dialogue_speakers`：逐条标注每句对话的说话人
  - `persons`：所有出现的人名（包含不说话的配角）
  - `organizations`、`locations`：组织和地点
  - `aliases`：角色别名映射

**步骤3：运行评估**
```bash
python analysis_reports/评估脚本/evaluate_generalization_v3.py \
  tests/test_novel_<类型>.txt \
  tests/test_novel_<类型>_ground_truth.json
```

**步骤4：记录结果**
- 将各项得分记录到 `analysis_reports/测试报告/泛化性测试报告_20260502_001700.md` 中
- 对比已有文体的得分，分析差异原因
- 如果某个模块得分低于 75，需要单独编写调试脚本定位问题

**GT 文件编写注意事项**:
- `speaking_persons` 是 NER 评估的关键，必须准确标注所有实际说话的角色
- `dialogue_speakers` 中的 `text` 字段只需截取对话的前 30 字即可
- 如果存在交织对话（同一行多人说话），需要拆分为多条记录
