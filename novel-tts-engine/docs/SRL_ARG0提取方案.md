## 一、信号源定位

**核心区分**——两个方案回答不同层面的问题：

| | 现有方案（规则提取） | SRL ARG0 提取 |
|:----|:--------|:---------|
| 提问 | 文本里提到了谁？ | 谁做了动作？ |
| 语义层级 | 词汇级（名字出现） | 句法级（谓词-论元） |
| 精度 | 中（需大量过滤） | 高（天然语法主语） |
| 召回 | 高（所有候选） | 低（只有主语） |
| 盲区 | 非人物误提取 | 无主语句无输出 |
| 对推理的价值 | 间接（角色出现了） | 直接（动作发出者 = 对话参与方） |

一句话说破：**现有方案回答"文本里提到了谁"，SRL 回答"谁做了动作"**。这两个集合有交集，但完全不同。

## 二、SRL ARG0 实测表现

### 2.1 测试命令

```python
import hanlp
doc = hanlp.load(hanlp.pretrained.mtl.CLOSE_TOK_POS_NER_SRL_DEP_SDP_CON_ELECTRA_SMALL_ZH)
r = doc('赵总监皱起眉头')
print(r['srl'])
# [[('赵总监', 'ARG0', 0, 2), ('皱', 'PRED', 2, 3), ('眉头', 'ARG1', 4, 5)]]
```

### 2.3 关键发现

1. **SRL 对"角色名+动作/说话动词"结构几乎 100% 正确** — 这正是说话人识别最需要的场景
2. **SRL 同时输出修饰版和干净版** — "疲惫的李经理"同时产出 `疲惫的李经理`(arg0_idx0-4) 和 `李经理`(arg0_idx2-4) 两种粒度
3. **无主语句子 SRL 不产生 ARG0** — 不会引入噪声，可安全 fallback 到现有路径
4. **非人物 ARG0 是主要噪声** — 需要 CHARACTER_BLACKLIST 过滤

## 三、方案架构

### 3.1 整体流程

```
旁白文本（context_before）
    ↓ ①
HanLP SRL 推理 → 提取所有 ARG0（按谓词去重）
    ↓ ②
┌─────────────────────────────────────────┐
│ _normalize_srl_arg0(raw_arg0, tokens)    │
│                                          │
│ 步骤A：去修饰语                          │
│  规则1：去除"的"前修饰                   │
│    "严肃的赵总监" → "赵总监"              │
│  规则2：去除动词短语前缀                   │
│    "穿西装的张总" → "张总"                │
│  规则3：去除介词/方位后缀                  │
│    "张总那边" → "张总"  "皮椅里" → "皮椅"  │
│                                          │
│ 步骤B：去头衔后缀                         │
│  如果归一化后名以 TITLE_WORDS 中任一头衔  │
│  结尾，尝试去除头衔并检查剩余部分有效性    │
│    "艾琳法师" → "艾琳"                   │
│    "亚瑟团长" → "亚瑟"                   │
│    "凯撒团长" → "凯撒"                   │
│    "莉莉治疗师" → "莉莉"                 │
│                                          │
│ 步骤C：非人物过滤                        │
│  CHARACTER_BLACKLIST 精确/部分匹配过滤    │
└─────────────────────────────────────────┘
    ↓ ③
角色库匹配（require_library=True）
    ↓ ④
加入候选池，置信度 = 距离衰减加权
  distance=0 → 0.90（同句主语，极强信号）
  distance=1 → 0.80（邻句主语，强信号）
  distance>1 → 0.65（远句主语，弱信号但有参考价值）
```

### 3.2 与现有路径的关系

```
                     旁白文本
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
      现有规则提取器             SRL ARG0 提取
    (谁被提到了)               (谁做了动作)
              │                       │
      ┌───────┴───────┐               │
      ▼               ▼               ▼
    NER PER     角色名模式          ARG0主语
    "赵总监"    "赵总监"           "赵总监"
    "李经理"     "笔记本" ❌
    "办公室" ❌
              │                       │
              └───────────┬───────────┘
                          ▼
                  候选池合并去重
                   （距离衰减加权）
                          │
                   _match_candidate_to_character
                   （含临时角色创建）
                          │
                      说话人推理
```

两条路径**并行独立**，互不依赖，在候选池合并时通过不同置信度加权区分优先级。

## 四、关键设计决策

### 4.1 为什么 SRL 推理不缓存到 NLPResult？

SRL 是临时结果，只服务于 `speaker_matcher.py` 的候选提取。如果缓存到 `NLPResult`，会增加 object 的复杂度和序列化负担。SRL 推理本身很快（~30ms/句），需要时直接调 `self.nlp.extract_srl_arg0s()` 即可。

### 4.2 为什么 require_library=True？

所有 SRL ARG0 候选必须映射到已注册角色，不创建临时角色。原因是：
1. SRL 提取的是完整的命名实体（不含部分匹配），非角色库角色说明不存在
2. 避免引入假阳角色污染角色库
3. 与现有描述性角色路径策略一致

### 4.3 为什么置信度用距离衰减而不是固定值？

**（V1 → V2 设计演进）**

第一版方案使用固定置信度 0.80，认为 SRL ARG0 比规则提取可靠即可。但后续分析发现一个问题：

> "赵总监看着窗外，雨越下越大。他转过身，对李经理说：'这件事到此为止。'"

SRL 提取到 ARG0 = "赵总监"（第一句主语）。但第一句只是环境铺垫，对话在第三句才开始。如果给固定 0.80，它会以不合理的优先级压过真正在对话中的李经理。

**核心结论**：SRL 的信号价值不是恒定的，而是 **f(距离)**——ARG0 所在句到对话句的距离越远，信号越弱。

```
距离为 0（同句） → ARG0 = 对话的说话人或直接参与方 → 0.90
距离为 1（邻句） → ARG0 在紧邻上下文中出现 → 0.80
距离 > 1（远句） → ARG0 只是背景环境描写中的主语 → 0.65
```

这个距离衰减保证了 SRL 在需要的地方比规则提取更可靠（0.90 > 0.75），在不需要的地方不会添乱（0.65 几乎不参与竞争）。

### 4.4 为什么仅用 context_before？

SRL ARG0 提取需要完整的谓词结构才能识别执行者。context_after 中的旁白通常是"XXX说道"之后的内容，谓词结构不完整。实测数据显示 context_after 中的描述性角色贡献较小（原描述性角色路径中 context_after 置信度仅 0.75）。

### 4.5 HanLP SRL 输出格式说明

SRL 输出结构：
```python
result['srl'] = [
    [  # 第一个谓词组
        ('赵总监', 'ARG0', 0, 2),   # (文本, 论元角色, start_token_idx, end_token_idx)
        ('皱', 'PRED', 2, 3),
        ('眉头', 'ARG1', 4, 5)
    ],
    [  # 第二个谓词组（多谓词句子）
        ('赵总监', 'ARG0', 0, 2),
        ('问道', 'PRED', 5, 6)
    ]
]
```

ARG0 文本基于 tok/fine（细粒度分词），索引指向 token 列表中的位置。

### 4.6 SRL 的双重定位

SRL 可以同时在两个层面发挥作用，互不冲突：

| 层面 | 角色 | 位置 | 行为 |
|:----|:----|:-----|:-----|
| **预处理层** | 角色发现 | `analyze_dialogue()` 开头 | 扫描全文，发现未注册角色，创建临时角色 |
| **候选信号层** | 置信度加权 | `_extract_context_speakers()` | 对已知角色，按距离衰减注入候选池 |

- **预处理层**：负责"发现未知"——把 SRL 发现的陌生角色名注册为临时角色，供后续对话匹配
- **候选信号层**：负责"已知角色加权"——对已注册角色，ARG0 身份意味着更高的置信度

### 4.7 文体自适应接入点（预留）

SRL 衰减速度可以作为文体自适应系统的第一个落地变量：

| 文体 | ARG0-对话重合度 | 衰减策略 | 说明 |
|:----|:--------------:|:---------|:------|
| 都市 | 高 | `[0.90, 0.85, 0.75]` | 动作=说话上下文，慢衰减 |
| 西幻 | 中 | `[0.85, 0.75, 0.65]` | 动作描写密集但有关联 |
| 修仙 | 低 | `[0.80, 0.65, 0.55]` | 大量独立动作描写，快衰减 |
| 历史 | 低 | `[0.80, 0.65, 0.55]` | 仪式性动作多 |

实现方式：`SRL_CONFIDENCE_BY_STYLE = {'都市': [0.90, 0.85, 0.75], '西幻': [...], ...}`

**注意**：文体自适应功能上次被搁置是因为"不知道如何落地"。SRL 的 ARG0 给了它一个干净的落地路径——**一件文体的差异可以简化为"一根参数（SRL 衰减速度）的差异"**，而不是为每个信号单独调参。当前阶段不实现，仅供参考记录。

## 六、风险

| 风险 | 概率 | 影响 | 应对 |
|:---|:---:|:---:|:---|
| SRL 模型未初始化 | 低 | 无 SRL 候选 | `extract_srl_arg0s()` 内部已加 `if not self._initialized` 保护 |
| SRL 推理异常 | 低 | 单句失败 | 用 try/except 包裹，静默失败 |
| ARG0 误提取非人物 | 中 | 假阳候选 | CHARACTER_BLACKLIST + require_library=True 双重过滤 |
| 修饰语去除不干净 | 中 | 无法匹配角色库 | require_library=True 会让匹配失败，不影响结果 |
| **长距离 ARG0 误判** | **中** | 以 0.65 置信度加入候选 | 距离衰减已压缩 >1 的场景为弱信号 |
| 性能下降 | 低~中 | 每章 +~200ms | 单次 SRL 推理 ~30ms，每章 ~5-10 个旁白段 |
