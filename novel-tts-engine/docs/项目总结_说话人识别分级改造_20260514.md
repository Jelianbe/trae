## 一、项目总览

### 1.1 目标

将说话人识别从纯规则系统（47.1%）改造为 **规则优先 + LLM 兜底（Hybrid）** 架构，预期准确率提升至 78-85%。

### 1.2 架构

```
PipelineRunner
  └─ HybridSpeakerMatcher（新增）
      ├─ SpeakerMatcher（LegacyRuleMatcher，保持不动）
      │   ├─ L1: 确定性规则（≥0.85）
      │   └─ L2: NLP 辅助规则（0.5-0.85）
      └─ L3: LLM 兜底（新增）
          └─ 仅当 L1+L2 返回 None 或 confidence < LLM_THRESHOLD(0.7)
```

### 1.3 核心原则

1. **`SpeakerMatcher` 一行不改** —— 已经稳定运行
2. **LLM 只在规则搞不定时才出场** —— 不可用时自动降级
3. **候选人质量决定一切** —— CharacterManager.build_candidate_list() 负责
4. **不建新映射表** —— 遵循 R-016 硬编码管理规则

## 三、Phase 2：HybridSpeakerMatcher（已实现）

### 3.1 文件

[H ybridSpeakerMatcher](file:///d:/trae/novel-tts-engine/pipeline/hybrid_speaker_matcher.py)（新文件）

### 3.2 核心逻辑

```python
def match_speaker(self, context: DialogueContext) -> Optional[MatchResult]:
    result = self.rule_matcher.match_speaker(context)

    if result is None:
        return self._llm_fallback(context)       # 规则失败 → LLM

    self._rule_match_count += 1

    if result.confidence < LLM_THRESHOLD:         # 0.7
        llm_result = self._llm_fallback(context)  # 规则不自信 → LLM 二次确认
        if llm_result and llm_result.confidence > result.confidence:
            return llm_result
        return result

    return result                                  # 规则自信 → 直接用
```

### 3.3 LLM 配置

| 参数 | 值 |
|------|-----|
| 模型 | Qwen/Qwen2.5-1.5B-Instruct |
| 硬件 | CPU（无 CUDA） |
| 加载方式 | 延迟加载，`local_files_only=True` |
| 置信度 | 固定 0.85（1.5B 无元认知能力） |
| max_candidates | 6 |
| LLM_THRESHOLD | 0.7 |
| System Prompt | 3 个 few-shot 示例（苏夜/赵天行/药老） |

### 3.4 关键设计问题（见后文第六节）

- `analyze_dialogue()` 是纯委托给 `rule_matcher.analyze_dialogue()`，不走 `match_speaker()` 路径
- 这意味着 pipeline 调用链中 LLM **从未被触发**

### 6.2 DialogueBoundaryDetector 误杀（P0 级）

#### 问题

`DialogueBoundaryDetector` 在修仙传真实文本上 **27 条引号仅放行 1 条**，误杀率 **96.3%**。

#### 触发链路

```
analyze_dialogue()
  → DIALOGUE_PATTERNS 提取 27 条引号
  → DialogueBoundaryDetector.detect_all() 过滤
  → 仅保留 1 条（is_dialogue=True）
  → 其余 26 条被判定为非对话，丢弃
  → speaker_matcher 只收到 1 条对话候选项
```

#### 根因

| 根因 | 误杀数量 | 说明 |
|------|:--------:|------|
| **策略1：15字窗口** | 22 条 | 说话动词距离引号远超 15 字（修仙文常见） |
| **策略2：省略号→内心独白** | 2 条 | "……"表示停顿/犹豫，不是内心独白 |
| **策略3：书本引用模式** | 2 条 | 匹配半径 30 字符过宽 |

#### 修复方案（已完成：[dialogue_boundary_detector](file:///d:/trae/novel-tts-engine/pipeline/dialogue_boundary_detector.py)）

**核心思路：将"判定对话/非对话"改为"只过滤高置信度非对话，其余全部放行"。**

具体修改（5 项）：

1. **策略1不再是抑制信号** —— 无说话动词时不扣分、不加抑制标签
2. **省略号不再作为抑制信号** —— 删除检查6
3. **单/双字词抑制仅对拟声词生效** —— 叠字检测（如"滋滋"）、专有后缀
4. **策略3缩小匹配半径** —— 从 30 字缩小到 15 字
5. **_detect_single 判定逻辑修改** —— 从"不确定时否定"改为"不确定时放行"

**预期效果**：27 条从 1 条→23 条（拟声词 3 条 + 地名 1 条继续过滤）

### 7.6 核心结论

1. **LLM benchmark 100% 是虚假指标** —— 理想条件（手动构建候选人 + 完美上下文）下的结果，不代表生产环境
2. **规则 confidence 不代表正确率** —— 规则在 16 条上自信（conf≥0.75）但全错，LLM_THRESHOLD（0.7）形同虚设
3. **LLM 1.5B 能力边界明确** —— 对一次性/临时角色完全无法判断，12 次调用全返回 `unknown`
4. **混合架构实际效果 = 纯规则** —— 45.1% vs 47.1%，差异在误差范围内
5. **Hybrid 不是银弹** —— 问题不在"LLM 不够"（benchmark 100%），而在于：**规则不会"示弱"**（永远是高分犯错），且 **LLM 在真实场景下远超 1.5B 的能力边界**

## 八、Hybrid 架构核心问题（根因分析）

### 8.1 `analyze_dialogue()` 是纯委托（架构级问题）

```python
# pipeline_runner 的调用链：
pipeline_runner.analyze_chapters()
  → runner.analyze_pipeline(chapter_text)
    → speaker_matcher.analyze_dialogue(content, chapter_id)
      → self.rule_matcher.analyze_dialogue(content, chapter_id)  # ← 纯委托！
        → ... → self.match_speaker(context)  # ← 调用 LegacyRuleMatcher 的 match_speaker
```

问题：`HybridSpeakerMatcher.analyze_dialogue()` 直接将控制权转交给 `rule_matcher`（LegacyRuleMatcher），而 `LegacyRuleMatcher.match_speaker()` **没有 LLM 兜底逻辑**。

所以 **pipeline 路径下 LLM 从未被触发**。

### 8.2 规则 confidence 不等于正确率（评估级问题）

| 条目 | 规则预测 | 是否正确 | confidence |
|------|---------|:--------:|:----------:|
| re_003 | 将军 | ❌（GT=韩将军） | **0.80** |
| re_006 | 黑甲 | ❌（GT=黑甲骑士） | **0.85** |
| re_024 | 苏夜 | ❌（GT=林雪） | **0.85** |
| re_037 | 萧炎 | ❌（GT=药老） | **0.85** |
| re_064 | 骑士 | ❌（GT=亚历山大·安德森） | **0.80** |

**规则系统的 confidence 衡量的是"匹配质量"（特征匹配度），不是"正确概率"**。规则的"自信"不表示答案正确。

### 8.3 Qwen2.5-1.5B 在真实场景能力不足

1. 对一次性角色（"杀手"、"讨债人"、"获救者"）——上下文不足时 LLM 也无法推断
2. 对描述性角色（"女修"、"年轻人"、"前辈"）——需要世界观知识，1.5B 模型不具备
3. benchmark 100% 是理想条件（预裁剪上下文 + 手动候选人），与生产条件差距大
