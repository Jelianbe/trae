## 一、改进背景与目标

### 1.1 当前问题诊断

基于近期评估报告和技术审查，项目存在以下核心问题：

| 问题类别 | 具体表现 | 影响程度 |
|---------|---------|---------|
| **功能膨胀** | 19个pipeline模块，部分功能非必需 | 高 |
| **测试框架缺陷** | 评估脚本与生产代码格式不匹配 | 高 |
| **数据库重复** | 两套CharacterManager实现 | 中 |
| **前端滞后** | Streamlit前端无法触发完整Pipeline | 高 |
| **产品化困难** | 功能过多导致无法快速发布MVP | 极高 |

### 1.2 改进目标

**核心目标**：从"技术完美主义"转向"产品实用主义"，在2-3周内交付可用的MVP版本。

**具体指标**：
- 功能模块从19个简化至6个核心模块
- 前端接口从复杂多级结构简化为扁平化输出
- 测试框架与生产代码完全对齐
- 数据库层统一为单一实现

### 2.2 简化后的Pipeline架构

```
输入: 小说文本 (.txt)
    ↓
[章节划分器] ChapterSplitter
    ↓ 输出: List[Chapter]
    
[NER分析器] NLPBasics (简化版)
    - 仅保留人名识别
    - 简化虚假人名过滤规则
    ↓ 输出: List[Entity]
    
[说话角色过滤器] SpeakerRoleFilter
    - 仅检查对话上下文
    - 移除高频实体特殊处理
    ↓ 输出: List[Entity]
    
[实体链接器] EntityLinker (简化版)
    - 仅保留精确匹配
    - 基础别名匹配
    ↓ 输出: List[LinkedEntity]
    
[说话人匹配器] SpeakerMatcher
    - 保留六级漏斗逻辑
    - 保持当前优化成果
    ↓ 输出: DialogueResult
    
[情绪标注器] EmotionTagger (降级版)
    - 接受28-30%准确率
    - 不做LLM混合优化
    - 置信度透明输出
    ↓ 输出: EmotionResult
    
[TTS生成器] KokoroTTSGenerator
    - 旁白/对话声线分离
    - 基础情绪驱动
    ↓ 输出: 音频文件
```

### 2.3 简化后的数据模型

#### 2.3.1 输出数据结构

```python
@dataclass
class SentenceData:
    """简化版句子数据结构"""
    text: str                      # 文本内容
    type: Literal["narration", "dialogue"]  # 仅两种类型
    speaker: str                   # 说话人（旁白为空字符串）
    emotion: str                   # 情绪标签：neutral/joy/anger/sadness/surprise/fear
    emotion_confidence: float      # 情绪置信度（0.0-1.0）
    sentence_id: int               # 句子序号

@dataclass
class ChapterResult:
    """简化版章节结果"""
    chapter_id: int
    title: str
    sentences: List[SentenceData]
    statistics: Dict[str, int]     # 仅保留基础统计
```

#### 2.3.2 数据库表结构（简化版）

```sql
-- 保留核心表
CREATE TABLE characters (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE,
    aliases TEXT,                  -- JSON数组
    gender TEXT DEFAULT 'unknown',
    voice_id TEXT,                 -- TTS音色ID
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE chapters (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    content TEXT,
    status TEXT DEFAULT 'pending',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE sentences (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    chapter_id INTEGER NOT NULL,
    sentence_index INTEGER NOT NULL,
    content TEXT NOT NULL,
    sentence_type TEXT,            -- narration/dialogue
    speaker_name TEXT,             -- 直接存储名字，简化外键关系
    emotion TEXT,
    emotion_confidence REAL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 移除非核心表
-- REMOVED: sfx_words（拟声词表）
-- REMOVED: progress（进度表，可用内存状态替代）
```

### 3.2 储备功能清单

#### 3.2.1 拟声词检测 (sfx_detector.py)

```markdown
## 功能概述
检测文本中的拟声词（轰隆、哗啦、滴答等），用于TTS音效标记

## 当前实现状态
- 词典规模：500+词条
- 检测准确率：80-90%
- 性能开销：低

## 移入原因
前端当前阶段仅需对话/旁白，拟声词不是核心需求

## 恢复条件
1. 产品进入v2.0阶段
2. 用户反馈需要音效增强
3. TTS引擎支持音效标记（如Kokoro升级）

## 恢复步骤
1. 将 sfx_detector.py 移回 pipeline/
2. 在 SentenceData 中恢复 sfx 字段
3. 在 pipeline_runner.py 中恢复调用逻辑
4. 更新前端展示逻辑（添加音效标记）

## 依赖关系
- 无独立依赖
- 与 TTS 生成器有集成点

## 预估恢复工时
- 代码恢复：30分钟
- 集成测试：1小时
- 前端适配：2小时
```

#### 3.2.2 引号内容分类 (quotation_classifier.py)

```markdown
## 功能概述
将引号内容分类为：对话(dialogue)/书面(written)/内心独白(thought)

## 当前实现状态
- 分类器类型：规则+置信度

2. 需要区分书面语和口语化表达

## 恢复步骤
1. 将 quotation_classifier.py 移回 pipeline/
2. 在 SentenceData 中恢复 quotation_type 字段
3. 修改情绪标注逻辑，考虑引号类型
4. 前端添加心理描写特殊样式

## 依赖关系
- 被 emotion_tagger.py 引用
- 影响情绪标注的上下文判断

## 预估恢复工时
- 代码恢复：1小时
- 集成测试：2小时
- 前端适配：4小时
```

#### 3.2.3 上下文多样性验证 (context_diversity_validator.py)

```markdown
## 功能概述
基于右邻字多样性统计验证实体有效性，防止误合并

## 当前实现状态
- 验证准确率：高
- 性能开销：中（需要扫描上下文）
- 主要用途：过滤"萧炎道"中的"道"

## 移入原因
功能过度工程化，NER基础过滤已足够支撑MVP

## 恢复条件
1. 实体识别准确率显著下降
2. 出现大量误合并问题
3. 处理长文本（1000章+）时准确率不足

## 恢复步骤
1. 将 context_diversity_validator.py 移回 pipeline/
2. 在 pipeline_runner.py 中恢复调用逻辑
3. 调整验证阈值（根据实际数据）

## 依赖关系
- 依赖 nlp_basics.py 的NER结果
- 影响 entity_linker 的输入

## 预估恢复工时
- 代码恢复：30分钟
- 阈值调优：2小时
- 回归测试：2小时
```

## 五、关键决策记录

### 5.1 决策1：保留28-30%情绪准确率

**决策内容**：情绪标注模块保持当前规则系统，不做LLM混合优化

**决策理由**：
1. LLM (Qwen2.5-1.5B) F1=0.722，规则系统 F1=0.723，几乎相同
2. 情绪标注任务本身存在固有难度，非规则设计问题
3. LLM混合方案开发成本高（3-5天），ROI低

**影响**：
- 情绪标注置信度透明输出，前端可决定是否使用
- v2.0再考虑更大LLM或BERT fine-tune

**决策日期**：2026-05-07

### 5.2 决策2：统一使用pipeline/character_manager.py

**决策内容**：移除db/db_utils.py中的CharacterManager，统一使用pipeline版本

**决策理由**：
1. pipeline版本功能更完整（性别推断、活跃度管理、别名合并）
2. pipeline版本使用dataclass，类型安全
3. 避免两套实现导致的数据不一致

**影响**：
- 需要更新所有引用db_utils.CharacterManager的代码
- 需要迁移现有数据

**决策日期**：2026-05-07

### 5.3 决策3：移除拟声词检测

**决策内容**：将sfx_detector.py移入战略储备库

**决策理由**：
1. 前端仅需对话/旁白，拟声词不是核心需求
2. 当前TTS引擎（Kokoro）不支持音效标记
3. 功能虽完成但无使用场景

**影响**：
- SentenceData移除sfx字段
- 输出JSON简化

**恢复条件**：TTS引擎支持音效标记，用户反馈需要

**决策日期**：2026-05-07
