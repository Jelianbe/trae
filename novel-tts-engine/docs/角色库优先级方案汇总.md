# 角色库优先级匹配方案汇总文档

> **文档日期**: 2026-05-09
> **目的**: 汇总角色识别流程现状及各优化方案，供决策参考
> **适用范围**: NovelTTS Cloud 说话人匹配模块

---

## 一、背景与问题

### 1.1 问题描述

NovelTTS Cloud 的角色识别系统支持用户提前在角色库中创建角色并分配语音。但在实际分析过程中，系统并未优先使用用户预设的角色库，导致：

1. **用户预分配角色未被充分利用**：用户手动创建并配置的角色可能被遗漏
2. **重复角色创建**：同一角色可能被系统多次创建（如"萧炎"和"炎儿"未被正确关联）
3. **用户体验不一致**：用户投入时间配置的角色库在分析中没有体现优先级

### 1.2 核心问题

> **用户问题**："我们的分析逻辑是否会有优先选择读取角色库？选择角色，然后优先依据角色库的角色参与识别和分配？"

## 二、当前实现现状（Original Scheme）

### 2.1 核心模块

#### `pipeline/speaker_matcher.py` — 说话人匹配器

**匹配策略链**（按优先级从高到低）：

```python
def match_speaker(self, context: DialogueContext) -> Optional[MatchResult]:
    # 步骤 1: 上下文推理
    if context.context_before or context.context_after:
        context_candidates = self._extract_context_speakers(...)
        if context_candidates:
            # 用角色库验证匹配
            char = self.char_manager.get_character_by_name(name, project_id)
            if char:
                return MatchResult(character=char, confidence=confidence, 
                                   match_type=f'context_reasoning:{reason}')

    # 步骤 2: speaker_hint 匹配（显式说话提示）
    if context.speaker_hint:
        if context.speaker_hint in ('他', '她'):
            result = self.match_by_pronoun(context.speaker_hint, context)  # 使用角色库
        else:
            result = self.match_by_name(context.speaker_hint)     # 精确匹配角色库
            if not result:
                result = self.match_by_alias(context.speaker_hint)  # 别名匹配角色库
            if not result:
                result = self.match_by_title(context.speaker_hint)  # 头衔匹配角色库
            if not result:
                # 匹配不到则创建新角色
                hint_char = self.char_manager.find_or_create(...)
                return MatchResult(character=hint_char, confidence=0.85,
                                   match_type='speaker_hint_created')

    # 步骤 3: 提及角色匹配
    mentioned = context.mentioned_characters or []
    for name in mentioned:
        result = self.match_by_name(name)   # 角色库精确匹配
        if not result:
            result = self.match_by_alias(name)  # 角色库别名匹配

    # 步骤 4: 语义匹配（使用角色向量）
    if context.chapter_id is not None and self.semantic_ranker.is_available():
        result = self.match_by_semantic(context.text)  # 计算与角色库的向量相似度

    # 步骤 5: 触发词匹配
    trigger_result = self.match_by_trigger_words(context.text, context)  # 使用角色库

    # 步骤 6: 称呼推理
    result = self._infer_from_address(context)  # 基于角色库推断

    return None
```

#### `pipeline/character_manager.py` — 角色管理器

**关键方法**：
| 方法 | 功能 |
|------|------|
| `get_character_by_name(name, project_id)` | 精确匹配角色名 |
| `get_character_by_alias(alias, project_id)` | 别名匹配（LIKE 查询） |
| `find_or_create(name, project_id)` | 匹配则返回，否则自动创建 |
| `add_character(name, project_id, ...)` | 新增角色 |
| `update_character(char_id, ...)` | 更新角色信息 |
| `merge_characters(primary_id, secondary_id)` | 合并重复角色 |

### 2.2 当前方案的优势

| 优势 | 说明 |
|------|------|
| ✅ **多策略覆盖** | 6 种匹配策略，适应不同文本场景 |
| ✅ **置信度体系** | 0.30~1.00 的置信度反映匹配可靠性 |
| ✅ **自动发现** | 无法匹配时自动创建新角色 |
| ✅ **别名支持** | 支持别名归一化到已知角色 |

### 2.3 当前方案的不足

| 不足 | 说明 |
|------|------|
| ❌ **无角色库优先扫描** | 没有在分析前预扫描角色库 |
| ❌ **无优先级区分** | 用户预分配角色和自动发现角色同等对待 |
| ❌ **依赖 NER 精度** | 角色匹配高度依赖 NER 识别准确率 |
| ❌ **缺乏用户控制** | 用户无法指定哪些角色应该被优先匹配 |

## 三、方案 A：另一个 AI 提供的方案 — 全局角色库预扫描

### 3.1 方案描述

在 `match_speaker` 最前面添加一个"角色库优先扫描"步骤：

```python

    if self._character_priority_mode:

        if result:
            return result
    
    # 原有流程...
```

**核心逻辑**：
```python
def _match_from_character_library(self, context: DialogueContext) -> Optional[MatchResult]:
    """从角色库中优先匹配说话人"""
    # 1. 获取所有角色，按优先级排序
    characters = self._get_characters_by_priority()
    
    for char in characters:
        # 2. 检查角色名是否在文本中
        if char.name in context.text:
            return MatchResult(
                character=char,
                confidence=0.9,
                match_type='character_library_priority'
            )
        
        # 3. 检查别名
        for alias in char.aliases:
            if alias in context.text:
                return MatchResult(
                    character=char,
                    confidence=0.85,
                    match_type='character_library_alias'
                )
    
    return None
```

### 3.2 优势分析

| 优势 | 影响程度 | 说明 |
|------|---------|------|
| 高置信度匹配 | 高 | 用户预分配的角色置信度可达 0.9~0.95 |
| 减少误创建 | 高 | 优先匹配已有角色避免重复创建 |
| 用户体验提升 | 中 | 用户配置的角色能被充分利用 |
| 音频分配一致性 | 高 | 预分配音色的角色正确匹配，避免音色漂移 |
| 别名归一化 | 中 | 利用角色库中的别名信息 |

### 3.3 劣势与风险

| 风险 | 严重程度 | 说明 |
|------|---------|------|
| **误匹配 (False Positive)** | 高 | 角色名可能是常见词（如"小明"、"老张"），全局扫描可能误判 |
| 破坏置信度体系 | 中 | 低质量但高优先级的匹配会污染置信度含义 |
| 性能损耗 | 低 | 每句话遍历角色库，O(N×M) 复杂度 |
| 覆盖 NER 发现 | 中 | 可能错过新角色的自动发现 |
| 维护成本增加 | 低 | 需要额外的优先级排序逻辑 |

### 3.4 适用场景对比

| 场景 | 当前方案表现 | 方案 A 表现 | 优劣 |
|------|------------|-----------|------|
| 用户预分配 5 个主要角色 | NER 识别到 3 个 | 5 个全匹配 | ✅ 方案 A 胜 |
| 新角色（未在角色库） | NER 自动发现 | 可能遗漏或延迟 | ❌ 当前方案胜 |
| 角色名是常见词 | NER 误判率低 | 可能误匹配 | ❌ 当前方案胜 |
| 用户合并了别名 | 别名匹配生效 | 同样生效 | = 平手 |

### 3.5 方案 A 总结

**结论**: 方案 A 提供了角色库优先的思路，但全局扫描的误匹配风险较高，且缺乏区分"高置信度角色"和"普通角色库角色"的机制。

## 四、方案 B：我的初始建议 — 增强现有策略权重

### 4.1 方案描述

**不添加新的匹配步骤**，而是在现有 `match_by_name` 和 `match_by_alias` 中增加权重：

```python
def match_by_name(self, name: str) -> Optional[MatchResult]:
    char = self.char_manager.get_character_by_name(name, self._current_project_id)
    if char:
        # 如果角色已分配语音，提升置信度
        base_confidence = 0.85
        if char.voice_assigned:
            base_confidence = 0.90  # +0.05 权重提升
        return MatchResult(character=char, confidence=base_confidence, match_type='name')
    return None
```

### 4.2 优势

| 优势 | 说明 |
|------|------|
| 实现简单 | 只需修改现有方法的置信度计算 |
| 风险低 | 不改变匹配流程，只调整权重 |
| 向后兼容 | 不影响现有功能 |

### 4.3 劣势

| 劣势 | 说明 |
|------|------|
| 效果有限 | 只提升 0.05 置信度，可能不足以改变匹配结果 |
| 依赖语音分配状态 | 需要额外存储 `voice_assigned` 状态 |

### 4.4 方案 B 总结

**结论**: 方案 B 实现简单但效果有限，适合快速验证，但不是最优解。

## 五、方案 C：用户控制锁定机制（推荐方案）

### 5.1 方案描述

**给角色库中的角色添加"锁定"功能**，由用户手动控制：

1. 用户创建角色后，可以手动"锁定"该角色
2. 分析时，系统优先匹配锁定角色
3. 锁定角色匹配成功返回高置信度
4. 未锁定角色走原有流程（方案 A 或方案 B）

### 5.2 核心设计

#### 数据库层面

在 `characters` 表添加 `is_locked` 字段：

```sql
ALTER TABLE characters ADD COLUMN is_locked INTEGER DEFAULT 0;
```

#### CharacterManager 新增方法

```python
def lock_character(self, char_id: int, project_id: str = '') -> bool:
    """锁定角色"""
    with self._get_connection() as conn:
        cursor = conn.cursor()
        cursor.execute(
            "UPDATE characters SET is_locked = 1, updated_at = CURRENT_TIMESTAMP WHERE id = ?",
            (char_id,)
        )
        conn.commit()
        return cursor.rowcount > 0

def unlock_character(self, char_id: int, project_id: str = '') -> bool:
    """解锁角色"""
    with self._get_connection() as conn:
        cursor = conn.cursor()
        cursor.execute(
            "UPDATE characters SET is_locked = 0, updated_at = CURRENT_TIMESTAMP WHERE id = ?",
            (char_id,)
        )
        conn.commit()
        return cursor.rowcount > 0

def get_locked_characters(self, project_id: str = '') -> List[Character]:
    """获取所有锁定角色"""
    with self._get_connection() as conn:
        cursor = conn.cursor()
        cursor.execute(
            "SELECT id, name, aliases, gender, first_appearance FROM characters "
            "WHERE project_id = ? AND is_locked = 1",
            (project_id,)
        )
        return [Character(
            id=row[0], name=row[1], aliases=set(json.loads(row[2])) if row[2] else set(),
            gender=row[3] or "unknown", first_appearance=row[4]
        ) for row in cursor.fetchall()]
```


```python
def _match_locked_characters(self, context: DialogueContext) -> Optional[MatchResult]:
    """优先匹配锁定角色"""
    locked_chars = self.char_manager.get_locked_characters(self._current_project_id)
    
    for char in locked_chars:
        # 精确匹配角色名
        if char.name in context.text:
            return MatchResult(
                character=char,
                confidence=0.95,
                match_type='locked_character_name'
            )
        
        # 匹配别名
        for alias in char.aliases:
            if alias in context.text:
                return MatchResult(
                    character=char,
                    confidence=0.90,
                    match_type='locked_character_alias'
                )
    
    return None
```

### 5.3 置信度体系

| 匹配类型 | 置信度 | 说明 |
|---------|--------|------|
| 锁定角色精确匹配 | 0.95 | 用户锁定 + 名字完全匹配 |
| 锁定角色别名匹配 | 0.90 | 用户锁定 + 别名匹配 |
| 上下文推理 + 角色库验证 | 0.85 | 原有流程最高置信度 |
| speaker_hint 匹配 | 0.80~0.85 | 显式说话提示 |
| 语义匹配 | 0.60~0.80 | 向量相似度 |
| 触发词匹配 | 0.65~0.70 | 触发词推断 |
| NER 自动发现 | 0.50~0.70 | 系统自动识别 |

### 5.4 优势分析

| 优势 | 影响程度 | 说明 |
|------|---------|------|
| **用户主权** | 高 | 用户手动加锁 = 明确意图，系统不应质疑 |
| **精准优先** | 高 | 锁定的角色才是真正的"高置信度角色" |
| **灵活控制** | 高 | 用户可加锁/解锁，系统不强制 |
| **性能友好** | 高 | 锁定角色数量可控（≤10），遍历成本低 |
| **语义清晰** | 中 | "锁定" = "优先匹配"，用户易理解 |

### 5.5 风险与缓解

| 风险 | 严重程度 | 缓解措施 |
|------|---------|---------|
| 锁定角色过多 | 低 | 建议上限 10~15 个，UI 提示 |
| 锁定角色与文本不匹配 | 低 | 允许用户事后解锁/调整 |
| 覆盖正确的 NER 结果 | 中 | 锁定角色优先，但 NER 结果仍作为备选 |

### 5.6 执行流程示例

```
场景 1：锁定角色匹配

用户锁定了 "萧炎" 和 "药老"

输入：「萧炎，你这丹药炼得如何？」药老捋着胡须问道。

步骤 0（锁定角色优先）：
  → 检查锁定角色 "萧炎" → 文本中存在 → 匹配成功，confidence=0.95
  → 返回 MatchResult(character=萧炎, confidence=0.95)

场景 2：无锁定角色匹配

输入：他缓缓睁开眼睛，眼中闪过一丝精芒。

步骤 0（锁定角色优先）：
  → 锁定角色都不在文本中 → 返回 None
  → 继续步骤 1（上下文推理）
  → 继续步骤 2（speaker_hint）...
  → 最终可能匹配到 NER 发现的新角色
```

### 5.8 方案 C 总结

**结论**: 方案 C 解决了"角色库优先"的核心问题（如何区分优先级），同时保留了 NER 的自动发现能力。用户控制感强，误匹配风险低，实现成本可控。
