## 1. SRL 应用准确率未提升的深入分析

### 1.1 问题概述

SRL（语义角色标注）ARG0 提取按 [SRL_ARG0提取方案.md](file:///d:/trae/novel-tts-engine/docs/SRL_ARG0提取方案.md) 实施后，经过多轮验证，**都市职场准确率基线未发生任何变化**（始终为 67.06%），西幻基线也保持在 53.8%。以下从三个层面分析原因。

### 1.2 主要原因一：原始 SRL 解析代码存在 Bug

#### 1.2.1 现象

HanLP 的 SRL 输出格式与代码预期严重不符。原始代码假设 SRL 输出为 `[(谓语词, start, end, [arguments_list]), ...]` 的格式，但实际输出为：

```python
# HanLP 实际输出（每个谓语一个 frame）
[('赵总监', 'ARG0', 0, 2),     # (文本, 论元角色, start_token_idx, end_token_idx)
 ('皱起', 'PRED', 2, 3),
 ('眉头', 'ARG1', 3, 4)]
```

#### 1.2.2 代码错误细节

原始代码使用 `pred_info[3]` 预期获取参数列表，但实际上 `pred_info[3]` 是一个 `(文本, 角色, start, end)` 元组——恰好回到框架内第4个元素，并且角色是 `ARG1` 而非 `ARG0`，导致所有 ARG0 全部在解析层被丢弃。

#### 1.2.3 修复与验证

修复后使用零样本测试验证 HanLP SRL 的实际提取能力：

| 测试项 | 结果 |
|------|------|
| 典型句式测试（19句） | 全部正确提取 ARG0 |
| 都市前文（91段） | SRL 触发率 **86.8%**（79/91段可提取到 ARG0） |
| 西幻前文（32段） | SRL 触发率 **87.5%**（28/32段可提取到 ARG0） |
| 都市 verbatim 匹配预期说话人 | 42次正确提取 |

#### 1.2.4 SRL 原始提取能力验证（典型句式）

| 输入 | SRL ARG0 | 评价 |
|:-----|:---------|:----:|
| 赵总监皱起眉头问道： | 赵总监 | 完美 |
| 李经理端起咖啡喝了一口 | 李经理 | 完美 |
| 亚瑟拔出长剑，高喊道： | 亚瑟 | 完美（多谓语共享主语） |
| 艾琳法师挥动法杖 | 艾琳法师 | 完美 |
| 他站起身，走到窗前： | 他 | 代词正确提取 |
| 赵总监对李经理点了点头 | 赵总监 | 多角色场景正确取主语 |
| 焦虑的李经理站起身 | 焦虑的李经理 | 含修饰语，需修剪 |
| 加文老战士握紧战斧 | 加文老战士 | 含职称，需修剪 |

**结论：HanLP 的 SRL 模块本身能力很强。代码 bug 是导致 ARG0 未被提取的唯一原因，不是 SRL 模型质量问题。**

### 1.3 主要原因二：SRL 不适合"候选竞争"模式

#### 1.3.1 本质差异

SRL ARG0 提取的是**语法主语**，而非"当前对话的说话人"：

| 原文 | SRL ARG0（主语） | 实际说话人 | 说明 |
|:----|:----------------:|:----------:|:----:|
| 赵总监看着李经理 | 赵总监 | 李经理 | ARG0≠说话人 |
| 这个项目我来负责 | 我(=说话人) | 赵总监 | 主语含对话引用 |
| 系统已经升级完成了 | _（无主语） | 吴工程师 | 无主语句 |

将 SRL 作为候选路径注入到 `_extract_context_speakers()` 的步骤 2.5，会让**语法主语**与现有路径中正确的**上下文说话人**在候选池中形成竞争。由于 SRL 提取的实体往往是前文中被提及的角色（而非当前说话人），在置信度排序中会干扰正确候选。

#### 1.3.2 数据验证

实验验证：将 SRL 作为候选路径步骤 2.5 激活（置信度 0.78），准确率变化：

| 测试集 | 基准准确率 | 加入 SRL 候选后 | 变化 |
|:------|:----------:|:---------------:|:----:|
| 都市职场 | 67.06% | 69.4% | +2.3%（不稳定） |
| 都市职场（独立测试） | 67.06% | 62.4% | -4.7%（过激发现模式） |
| 都市职场（收敛版本） | 67.06% | 67.06% | ±0% |

第一轮使用 `require_library=True`（无发现）略有提升但非常接近误差范围。第二轮使用 `allow_discovery=True`（角色发现模式）导致大量泛称（总监、女人、年轻人等）注册为临时角色，准确率暴跌到 62.4%。第三轮将 SRL 从候选竞争路径改为预处理角色发现后，回到 67.06%。

#### 1.3.3 关键因素总结

| 因素 | 影响程度 | 说明 |
|:----|:--------:|:----:|
| SRL 提取语法主语而非说话人 | 🔴 核心 | 与说话人识别的目标存在本质偏移 |
| 非人物 ARG0 噪声 | 🟠 高 | SRL 提取"项目""预算""数据"等非人物 |
| 修饰语增加匹配难度 | 🟡 中 | "焦虑的李经理"需要修剪才匹配"李经理" |
| 角色库限制 | 🟡 中 | require_library=True 封锁零样本发现能力 |
| 置信度竞争 | 🟡 中 | 0.78 置信度与现有路径（0.75~0.88）冲突 |

### 1.4 最终方案：SRL 定位调整

经过多轮实验，SRL 最终定位为**预处理角色发现工具**（而非候选竞争路径），并在 `analyze_dialogue()` 开头激活：

```
输入文本
    ↓
SRL 角色发现 → 提取 ARG0 → 通过人物过滤 → 注册临时角色
    ↓
逐段对话匹配（原有流程：前缀NER → 代词消解 → 描述性角色 → 自称推断 → 语境优先 → 动态候选）
    ↓
输出结果
```

这一方案的优势：
1. **零准确率退化** — 不影响已有 67.06% 的基线
2. **零样本发现** — 在无预注册角色库的真实场景中，SRL 从旁白中直接发现新角色
3. **下游路径自然继承** — 注册的临时角色被代词消解、动态候选等后续路径自动使用

### 1.5 实测 vs 预期对比表格

| 维度 | 预期（方案文档） | 实际 | 偏差根因 |
|:----|:----------------|:----|:---------|
| 都市准确率 | +6~9% | ±0% | 步骤2.5候选竞争策略错误 |
| 西幻准确率 | +2~6% | ±0% | 同上 + 西幻错误分布在对话轮换逻辑 |
| SRL提取能力 | ~100% | 86.8%触发率 | 代码bug修复后验证OK |
| 非人物过滤 | 少量噪声 | 大量误提取 | 需补充CHARACTER_BLACKLIST规则 |
| 修饰语修剪 | 规则3条 | 已实现1条（"的"分割） | "穿西装的张总"等复杂修饰需增强 |

## 2. 候选路径竞争问题详细阐述

### 2.1 竞争问题的具体表现

#### 2.1.1 "总监"独立实体竞争

这是当前基线 67.06% 中最大的系统性错误。在下面场景中反复出现：

```
前文旁白: 总监微笑着说
预测输出: "总监"   ← 被作为独立实体进入角色库 → 竞争压过正确预测
正确答案: "赵总监"
```

测试数据显示，**28 条错误中有 20 条**的预测为"总监"而非"赵总监"（索引 1, 8, 23, 27, 29, 31, 43, 45, 49, 50, 53, 66, 69, 76, 83, 84, 85, 91）。

#### 2.1.2 错误模式分布

从 baseline_result.json 的 28 条 WRONG 结果中统计：

| 错误模式 | 出现次数 | 占比 | 典型索引 |
|:--------|:--------:|:----:|:--------:|
| "总监"替代"赵总监" | 20次 | **71.4%** | 1,23,27,29,31,43,45,49,50,53,66,69,76,83,84,85,91 |
| "女人"误预测 | 4次 | 14.3% | 80,81,86,87,89,90 |
| "杯子"误预测 | 1次 | 3.6% | 9 |
| 其他角争 | 3次 | 10.7% | 10,14,34,39,55 |

#### 2.1.3 "总监"错误的产生根源

通过链路追踪分析，`_match_candidate_to_character` 将"总监"匹配为"赵总监"的别名：

```
原始候选路径 → "总监"   → _match_candidate_to_character("总监")
                          → get_character_by_alias("总监", project_id)
                          → 角色库中 "赵总监" 的别名包含 "总监"
                          → 返回 Character("赵总监")
                          → 但最终显示为 "总监"
```

问题路径：在角色库中，"赵总监"的别名集合包含 `{"总监", "赵总"}`。但当 NER 或描述性角色提取从旁白"总监微笑着说"中提取到"总监"时，`_match_candidate_to_character` 会通过别名匹配返回 `赵总监` 的 Character 对象。后续流程中 `char.name` 应为 "赵总监"，但中间步骤显示为"总监"一词。

跟踪 trace 表明，**`_match_candidate_to_character` 的 `context_reasoning` 路径在部分情况下未能正确映射到 `char.name`**，而是使用了匹配文本。

### 2.2 影响程度

| 指标 | 值 | 说明 |
|:----|:---:|:-----|
| 受影响对话数 | 20/91 | 21.9% 的对话受"总监"错误影响 |
| 可挽回数 | 20 | 如修复，准确率可提升 67.06% → **89.4%** |
| 对西幻影响 | 低 | 西幻主要错误在对话轮换逻辑（44.4%）和代词消解（22.2%） |

### 2.3 产生原因

1. **角色库别名反向匹配不精确** — "总监"作为"赵总监"的别名，反向匹配时不应视为精确匹配
2. **NER 提取粒度粗** — 旁白中"总监"的人名实体提取未结合上下文确认全名
3. **无最小匹配长度约束** — 2字职称作为3字角色名的别名时应设置前置匹配条件
4. **context_reasoning 路径缺少完整性校验** — 匹配后未检查匹配文本与 `char.name` 的一致性

### 2.4 已采取的措施

| 措施 | 效果 | 状态 |
|:----|:----|:----:|
| 尝试在 CHARACTER_BLACKLIST 增加"客户""项目""同事"等 | 不影响"总监"问题 | ❌ 无效 |
| SRL 从候选竞争改为预处理发现 | 消除第二类噪声 | ✅ 有效但不解决"总监" |
| 添加 `_trim_srl_modifier` 修饰语修剪 | 对 SRL 有效 | ✅ 但非"总监"问题的修复 |

### 2.5 计划采取的应对措施

| 优先级 | 措施 | 预期收益 | 复杂度 |
|:-----:|:-----|:--------:|:------:|
| P0 | 修复 `_match_candidate_to_character` 别名匹配精确性，保证匹配结果始终输出 `char.name` | +20条（准确率67.06%→89.4%） | 低 |
| P0 | 避免职称作为唯一匹配依据：当匹配文本是纯职称词（总监/经理/秘书）且角色库有多个含该职称的角色时，降低置信度 | +5~10条（防止残留） | 中 |
| P1 | NER 前后文拼合：当 NER 只提取到"总监"时，检查前文是否有更完整的人名 | +3~5条 | 中 |

### 3.4 风险与挑战

#### 🔴 风险-01: "总监"别名匹配修复可能引入新回归

- **概率**: 中
- **影响**: 共 14 条 OK 结果中如有依赖别名匹配"总监"→"赵总监"的路径，可能被影响
- **应对**: 修复后立即运行 pytest 回归测试，对比准确率

#### 🟠 风险-02: 西幻文体本身的语义模糊性

- **概率**: 高
- **说明**: 西幻测试集中 44.4% 的错误是"对话轮换逻辑"问题，这些错误源于小说本身未明确标注说话人（连续对话的默认轮换）
- **应对**: 采用宽松评估模式（relaxed mode）验证上限，如果 70% 目标达不到则调整到 65%

#### 🟠 风险-03: SRL 在无角色库场景的实际收益未被验证

- **概率**: 中
- **说明**: 当前所有测试集都基于预注册角色库。SRL 发现模式的真实收益需要在无角色库的场景中测试，但当前缺少对应的标注测试数据
- **应对**: 需要创建无角色库版本的测试集（清理预注册步骤）

#### 🟡 风险-04: P0 性能优化未产生可量化收益

- **概率**: 低
- **说明**: 3个P0性能优化在测试环境中无法验证端到端性能提升（单章处理已快于10秒）
- **应对**: 大数据量场景（处理完整长篇小说）时才可见效，标注为"储备"
