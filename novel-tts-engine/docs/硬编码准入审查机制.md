# 硬编码准入审查机制

**文档编号**: HARDCODE-REVIEW-001  
**生效日期**: 2026-05-13  
**适用范围**: novel-tts-engine 所有 pipeline/ 和 utils/ 下的 Python 文件

---

## 一、核心原则

根据项目核心规范，所有代码必须遵守以下原则：

1. **通则推理**: 优先使用句法、词性、标点等通用语言特征做判断，关键词只能是辅助信号，绝不能作为唯一依据
2. **不建新映射表**: 禁止新增任何"A→B"形式的静态映射表。如果确实需要将自称词关联到角色，只能通过上下文推理，找不到就标记为未知
3. **未知优于误判**: 当置信度不足或证据缺失时，必须诚实返回"未知"或低置信度结果
4. **语言学/统计学依据**: 任何保留的静态集合必须有明确来源——写清楚来源和边界

---

## 二、硬编码分类定义

### 2.1 禁止类（一律不得新增）

| 类型 | 示例 | 替代方案 |
|------|------|---------|
| A→B 业务映射表 | `{'三人': 'GROUP:3', '众人': 'GROUP:CROWD'}` | 正则+数量提取/句法检测 |
| 枚举型映射 | `{'他': 'male', '她': 'female'}` | 语言学封闭集可接受，但必须有来源注释 |
| 经验型阈值 | `if score > 0.5: ...` | 必须外置到 config.py |

### 2.2 需审批类（新增必须走审批流程）

| 类型 | 示例 | 审批条件 |
|------|------|---------|
| 静态词表 | `TITLE_WORDS = {'管家', '少爷', ...}` | 必须说明来源、边界、上限 |
| 正则模式 | `re.compile(r'...说道')` | 必须说明语言学依据 |
| 置信度阈值 | `CONFIDENCE_THRESHOLD = 0.5` | 必须外置到 config.py |

### 2.3 可接受类（无需审批，但须有来源注释）

| 类型 | 示例 | 条件 |
|------|------|------|
| 语言学封闭集 | 人称代词、标点符号 | 必须是语言学公认的封闭集合 |
| 统计发现的常量 | 基于全文扫描发现的阈值 | 必须标注统计来源 |
| 协议/标准常量 | GB/T 15834-2011 标点规范 | 必须标注标准编号 |

## 三、准入审批流程

### 3.1 审批触发条件

当代码中包含以下任一模式时，必须触发审批：

```python
# 模式1: 新建集合/列表/字典
CONSTANT_NAME = {'...', '...'}  # set
CONSTANT_NAME = ['...', '...']  # list (非常量)
CONSTANT_NAME = {'key': 'value'}  # dict

# 模式2: 硬编码数字阈值
if score > 0.5:  # 魔法数字

# 模式3: 硬编码正则模式
re.compile(r'(?:说道|道|问)')
```

### 3.2 审批检查清单

提交代码前必须回答以下问题：

```
□ 1. 这个词表是否可以用语言学/统计学方法替代？
     如果能 → 改造为统计方法，不需要词表
     如果不能 → 继续

□ 2. 这个词表是否有明确的来源？
     来源类型：
     - [ ] 语言学分类（如百家姓、现代汉语代词体系）
     - [ ] 国家标准（如 GB/T 15834-2011 标点符号用法）
     - [ ] 统计结果（如基于X文本统计的Y词出现频率≥Z）
     - [ ] 经验总结（需说明推导过程）
     → 在代码注释中标注来源

□ 3. 这个词表的边界是否清晰？
     - [ ] 哪些东西应该往里加
     - [ ] 哪些东西不应该往里加
     - [ ] 是否有上限约束
     → 在代码注释中标注边界

□ 4. 如果是阈值，是否已外置到 config.py？
     - [ ] 是（已在 config.py 定义）
     - [ ] 否（需要迁移到 config.py）

□ 5. 这个词表是否违反"不建新映射表"原则？
     - [ ] 否（不是 A→B 映射）
     - [ ] 是（需要改造为统计/推理方法）
```

### 3.3 标准注释模板

所有硬编码词表必须使用以下格式：

```python
# CONSTANT_NAME
#
# 用途：[这个词表用来做什么]
# 来源：[基于什么文献/统计数据/语言学分类]
# 边界：
#   - [哪些东西应该往里加]
#   - [哪些东西不应该往里加]
# 上限：[约N条/词，不应无限制扩容]
# 更新日期：[YYYY-MM-DD]
# 维护者：[维护此词表的规则/责任人]
CONSTANT_NAME = {'...', '...'}
```

### 3.4 审批决策

| 情况 | 决策 |
|------|------|
| 所有检查项通过 | ✅ 允许合并 |
| 可以用统计方法替代但未改造 | ❌ 拒绝，必须改造 |
| 无来源注释 | ❌ 拒绝，补充注释 |
| A→B 映射表 | ❌ 拒绝，必须改造 |
| 阈值未外置 | ⚠️ 要求迁移到 config.py |

## 四、技术债务管理

### 4.1 技术债务标记格式

所有已存在但尚未完全符合规范的硬编码，必须标记为技术债务：

```python
# TODO-HARDCODE [HC-001]: 此词表缺少来源注释
# 责任人: [负责人]
# 截止日期: [YYYY-MM-DD]
# 回退条件: [满足什么条件时必须改造]
```

### 4.2 回退条件定义

每个技术债务必须定义回退条件：

```
如果满足以下任一条件，必须立即改造此硬编码：
1. 统计方法已能覆盖此词表 90% 以上的场景
2. 词表条目超过上限的 2 倍
3. 新增条目时需要频繁修改此词表（每月 > 2 次）
```

### 4.3 战略储备库

被否决但值得保留的硬编码改造方案，存入战略储备库。详见 [硬编码战略储备库](硬编码战略储备库.md)。

## 五、违规处理

### 5.1 违规等级

| 等级 | 定义 | 处理 |
|------|------|------|
| P0-严重 | 新增 A→B 映射表 | 立即拒绝 PR，必须改造 |
| P1-高 | 新增硬编码无来源注释 | 要求补充注释后重新提交 |
| P2-中 | 新增阈值未外置到 config | 要求迁移后重新提交 |
| P3-低 | 注释格式不规范 | 建议修改，非强制 |

### 5.2 审查责任

- 代码审查者必须检查硬编码合规性
- AI 助手在生成代码时必须自动应用审批检查清单
- 自动化扫描脚本应在 CI 阶段拦截 P0/P1 违规
