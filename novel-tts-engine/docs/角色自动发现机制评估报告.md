## 一、问题背景

### 1.1 核心痛点

当前系统存在严重的**角色冷启动问题**：用户必须先手动预注册所有角色到角色库，系统才能进行说话人识别。这在实际使用中不可行——用户不可能费时费力地预先填充角色库。

### 1.2 问题发现过程

| 测试场景 | 准确率 | 发现角色数 | 结论 |
|---------|--------|-----------|------|
| 都市职场（有预注册） | 81.2% (69/85) | N/A | 基线 |
| 都市职场（无预注册） | 0.0% (0/85) | 0个 | 完全失败 |
| 西幻（有预注册） | 53.8% (21/39) | N/A | 基线 |

无预注册时准确率为 0%，说明系统**完全依赖角色库中已有角色**，缺乏自动发现能力。

## 三、核心问题深度分析

### 3.1 频率过滤机制（H-20260516-10）

#### 3.1.1 设计意图

为角色候选池引入频次过滤机制：每个角色名在文本中被提及时计数器+1，当计数器 < `CHARACTER_ELIGIBLE_MIN_FREQ` (=5) 时，该角色不进入匹配候选池。目的是过滤一次性临时角色（服务员、路人等），提高候选池信噪比。

#### 3.1.2 实验结果

| 指标 | 基线 | 改后 | 变化 |
|------|------|------|------|
| 长文本准确率 | 51.8% (44/85) | 51.8% (44/85) | ±0% |
| 短文本准确率 | 75.3% (183/243) | 75.3% (183/243) | ±0% |

**最终决策**: ❌ 已回退 — "设计正确但当前测试无法验证"

#### 3.1.3 失败根因

**不是机制无效，而是测试策略不匹配**：

| 场景 | 原因 | 结果 |
|------|------|------|
| 有预注册时 | 所有角色 `freq==0`（预注册角色），永远在 eligible 列表中 | 过滤从未生效 |
| 无预注册时 | 角色库为空，eligible 列表永远为空 | 过滤从未被测试 |
| 真实测试场景 | 应该**部分预注册 + 动态发现新角色** | 未验证 |

**根本原因**：当前系统的架构假设"角色库已预先填充"，但真实场景需要"从文本中自动发现角色"。这两个架构的差距导致频次过滤机制无法被正确验证。

#### 3.1.4 合理性评估

| 维度 | 评估 | 说明 |
|------|------|------|
| 目标一致性 | ⭐⭐⭐ 中 | 理论上能提升候选池质量，但与当前测试集不匹配 |
| 技术可行性 | ⭐⭐⭐⭐ 高 | 实现清晰，不影响数据库 Schema |
| 投入产出比 | ⭐ 极低 | 零收益，测试集预注册了所有角色 |
| 风险可控性 | ⭐⭐⭐⭐ 高 | 零退化，可安全回退 |
| 战略价值 | ⭐⭐⭐ 中 | 在真实长文本场景（非预注册）中可能有效 |

**最终结论**：
- ❌ 当前阶段不适用 — 测试环境无法验证，不应保留
- ✅ 战略储备价值 — 在真实生产长文本（角色数量庞大、临时角色频繁出现）中值得重新评估
- 📦 建议存入战略储备库，启动条件：角色库数量 > 50 且临时角色导致候选池信噪比下降

### 3.3 引号内容处理（`[对话]` 占位符，H-20260516-11 改动1）

#### 3.3.1 改动背景

早期版本在构建 `context_before` 时，会直接跳过含引号的行，或保留原始引号内容。这导致：
1. **上下文断裂**：旁白前缀（如 `赵总监揉了揉太阳穴：`）丢失，语境角色匹配失败
2. **引号内容污染**：原始对话内容进入上下文，被实体提取器误识别为角色名或动作主语

#### 3.3.2 改动方案

在测试解析层使用正则替换：`re.sub(r'["""](.+?)["""]', '[对话]', prev_line)`
- 保留含引号的行到 `context_before` 中
- 将引号内容统一替换为 `[对话]` 占位符
- 保留旁白前缀结构

#### 3.3.3 技术表现

| 场景 | 处理结果 | 评估 |
|------|---------|------|
| 标准对话：`亚瑟问道："敌军还有多久？"` | `亚瑟问道：[对话]` | ✅ 完美保留旁白 |
| 复合行：`"对话1"张总侧过身，"对话2"` | `[对话]张总侧过身，[对话]` | ✅ 保留中间旁白 |
| 拟声词：`"轰！"城墙外传来巨响` | `[对话]城墙外传来巨响` | ❌ 误标为对话 |
| 强调词：`我们必须'谨慎行事'` | `我们必须[对话]` | ❌ 误标为对话 |

#### 3.3.4 潜在风险

| 风险编号 | 风险描述 | 可能性 | 影响 | 等级 |
|----------|---------|--------|------|------|
| RQ-1 | 拟声词被分配说话人，导致匹配错误 | **已发生** | 高 | **P0** |
| RQ-2 | 强调引号干扰连续对话逻辑 | 中 | 中 | P1 |
| RQ-3 | `[对话]` 字符串被实体提取器误识别 | 低 | 中 | P2 |
| RQ-4 | 生产环境与测试解析逻辑不同步 | 中 | 高 | **P1** |

**西幻测试集实证**：
| 行号 | 原文 | 预期 | 预测 | 错误类型 |
|------|------|------|------|---------|
| 31 | `"轰！"` | 亚瑟（或跳过） | 雷恩 | 拟声词被当作对话匹配 |
| 33 | `"叮——"` | 雷恩（或跳过） | 艾琳 | 拟声词被当作对话匹配 |

#### 3.3.5 合理性评估

| 维度 | 评估 |
|------|------|
| 改动本身是否合理 | ✅ 合理且必要。解决了 context_before 信息丢失的核心痛点 |
| 当前实现是否完善 | ❌ 不完善。缺乏引号类型细分，导致拟声词/强调词误判 |
| 是否符合设计初衷 | ⚠️ 部分符合。保留了结构，但未实现语义分类 |
| 是否需要回退 | ❌ 不需要回退。净收益为正，回退会导致7条错误复现 |
| ROI | ⭐⭐⭐⭐⭐ 极高。低成本高回报，但存在技术债务 |

**综合判定**：该改动是**正确的工程决策**，属于"先解决有无，再优化精度"的典型路径。当前问题不是方向错误，而是**粒度不足**。

#### 3.3.6 改进建议

**方案1：轻量级引号预分类（推荐）**

```python
def classify_quotation(quote_text: str) -> str:
    """引号内容分类，返回类型标签"""
    # 拟声词特征：短（≤4字）+ 感叹号/破折号 + 无完整主谓结构
    if len(quote_text) <= 4 and re.search(r'[！!———…]+$', quote_text):
        return '[音效]'
    # 强调词特征：短 + 抽象词/副词 + 无动作主语
    if len(quote_text) <= 6 and not re.search(r'[的得了着过]', quote_text):
        return '[强调]'
    # 默认：对话
    return '[对话]'
```

**预期效果**：
- 修正拟声词误判（西幻2条）
- 修正强调引号干扰
- 产出明确的类型标记，供下游模块使用

### 3.4 连续对话识别问题

#### 3.4.1 错误类型分布

| 错误类型 | 城市职场 | 西幻 | 合计 | 占比 |
|---------|---------|------|------|------|
| 连续对话误继承 | 9条 | 3条 | 12条 | 48% |
| 称呼语误判 | 7条 | - | 7条 | 28% |
| 描述性角色干扰 | - | 4条 | 4条 | 16% |
| 拟声词误判 | - | 2条 | 2条 | 8% |

**连续对话误继承是最大的错误类型，占所有错误的48%。**

#### 3.4.2 中文连续对话的三种模式

| 模式 | 示例 | 特征 |
|------|------|------|
| **ABAB型** | A说→B说→A说→B说 | 两人交替对话 |
| **AAAA型** | A说→无旁白→无旁白→无旁白 | 一人连续说 |
| **AAAAB型** | A说→无旁白→无旁白→B说 | 一人连续说后切换 |

#### 3.4.3 历史修改策略的问题

| 问题 | 描述 |
|------|------|
| **改动只做了"一半"** | H-20260516-11 的连续对话逻辑只在测试解析层做了（构建 context_before），实际匹配逻辑未实现 |
| **对话轮换模型过于简单** | H-20260515-05 假设"上一个说话人不应该连续说"，只考虑 ABAB，无法处理 AAAA/AAAAB |
| **描述性角色优先级过高** | `_extract_context_speakers()` 提取的描述性角色覆盖了正确推理 |

#### 3.4.4 用户新方案评估

用户提出的"**识别首句旁白 → 确定说话人数量 → 连续继承 → 遇到新旁白重新识别**"方案方向正确：

| 维度 | 评估 |
|------|------|
| 目标一致性 | ⭐⭐⭐⭐ 高。直接命中最大错误类型（48%） |
| 技术可行性 | ⭐⭐⭐⭐ 高。实现简单，O(n)遍历 |
| 投入产出比 | ⭐⭐⭐⭐⭐ 极高。低成本高回报 |
| 风险可控性 | ⭐⭐⭐ 中。复杂场景（多人交替无旁白）可能误判 |

**需要补充的细节**：
1. 如何判断说话人数量（建议通过 context_before 中角色名出现次数）
2. 拟声词识别（"轰！"、"叮——"应返回"未知"）
3. 新旁白出现后的重新推理策略
4. 最大继承深度限制（建议≤3行）

### 3.5 姓氏匹配法的根本缺陷

系统曾尝试用**姓氏规则增强**来解决角色发现问题，但存在以下问题：

| 问题 | 示例 | 影响 |
|------|------|------|
| **截断错误** | "赵总监" → "赵总" | 角色名不完整 |
| **缺乏泛化能力** | 西幻"凯撒团长"不受影响，但都市"赵总监"被破坏 | 文体适应性差 |
| **违反设计原则** | 依赖硬编码姓氏表 | 违背"用语境和句法判断"原则 |
| **单字扩展污染** | "赵"+"总"→"赵总" | `_expand_single_char_entities` 制造错误 |

**已禁用规则**（2026-05-16）：
- `_detect_surname_based_entities`：姓氏+职位组合
- `_expand_single_char_entities`：单字姓氏扩展

**替代方案**：使用 SRL 语义角色标注提取完整角色名

## 四、SRL 角色发现方案验证

### 4.1 SRL 原理

**HanLP SRL（语义角色标注）** 能准确识别句子的动作执行者（ARG0）：

| 文本 | SRL ARG0 | 结果 |
|------|---------|------|
| 赵总监皱起眉头 | "赵总监" | ✅ |
| 李经理回答 | "李经理" | ✅ |
| 凯撒团长说道 | "凯撒团长" | ✅ |
| 艾琳法师翻开魔法卷轴 | "艾琳法师" | ✅ |

**优势**：
- 不依赖姓氏表
- 自动提取完整名称
- 语义理解而非规则匹配
- 适用于所有文体

## 六、优化方案

### 6.1 方案1：SRL 非人物 ARG0 过滤（解决 P0-1）

**原理**：基于词性和语义类别过滤非人物 ARG0。

**过滤规则**：
1. **物品名词**：排除包含"室"、"本"、"椅"、"杯"、"符"、"文"等字眼的 ARG0
2. **身体部位**：排除"眼睛"、"手"、"头"、"脚"等
3. **抽象概念**：排除"声音"、"光芒"、"气息"、"数据"等
4. **占位符**：排除包含 "[" 或 "]" 的 ARG0
5. **介词短语**：排除以"在"、"上"、"里"、"边"结尾的 ARG0

**实现位置**：`speaker_matcher.py` 的 `_extract_from_srl()` 方法

**预期效果**：过滤掉 80%+ 的非人物 ARG0

### 6.2 方案2：角色名去修饰语（解决 P0-2）

**原理**：从 SRL ARG0 中提取核心角色名，去除修饰语。

**规则**：
1. **去除"的"前修饰**："严肃的赵总监" → "赵总监"
2. **去除动词短语**："穿西装的张总" → "张总"
3. **去除形容词**："疲惫的李经理" → "李经理"
4. **保留核心名词**：使用 HanLP 分词+词性标注，只保留 NR（人名）+ 头衔

**实现位置**：`speaker_matcher.py` 的新方法 `_normalize_character_name()`

**预期效果**：将带修饰语的 ARG0 归一化为核心角色名

### 6.3 方案3：角色名头衔归一化（解决 P0-3）

**原理**：建立头衔后缀表，从角色名中去除头衔。

**头衔后缀表**：
```python
TITLE_SUFFIXES = {
    '团长', '法师', '战士', '老战士', '治疗师', '队长', '导师', '骑士',
    '总监', '经理', '秘书', '工程师', '总', '工',
    # 可扩展
}
```

**归一化逻辑**：
1. 检查角色名是否以头衔后缀结尾
2. 如果是，尝试去除后缀，检查剩余部分是否为有效角色名
3. 保留核心名和全名两种形式（用于别名匹配）

**实现位置**：`speaker_matcher.py` 的 `_normalize_character_name()` 方法

**预期效果**：将"亚瑟团长"归一化为"亚瑟"，准确率提升 10-15%

### 6.4 方案4：引号内容分类（解决 P0-5）

**原理**：在 `[对话]` 替换前，增加引号类型分类。

```python
def classify_quotation(quote_text: str) -> str:
    if len(quote_text) <= 4 and re.search(r'[！!———…]+$', quote_text):
        return '[音效]'
    if len(quote_text) <= 6 and not re.search(r'[的得了着过]', quote_text):
        return '[强调]'
    return '[对话]'
```

**预期效果**：修正拟声词误判（2条），消除强调引号干扰

### 6.5 方案5：连续对话逻辑精细化（解决 P0-4）

**原理**：基于旁白边界的连续对话块识别。

**三种模式处理**：
1. **ABAB型**：正常交替
2. **AAAA型**：连续继承首句说话人
3. **AAAAB型**：连续继承到下一个旁白出现时切换

**实现要点**：
- 增加最大继承深度（建议≤3行）
- 新旁白出现后重新推理
- 拟声词识别（返回"未知"）

**预期效果**：修正 12 条连续对话错误（48%错误类型）

### 6.6 方案6：称呼语排除优化（解决 P1-3）

**原理**：识别对话开头的称呼模式，将称呼排除出说话人候选。

**预期效果**：修正 7 条称呼语误判（28%错误类型）

## 八、结论与建议

### 8.1 核心结论

1. **SRL 角色发现方向正确**：相比 NER+姓氏规则，SRL 能提取完整角色名，不依赖硬编码表
2. **当前实现是"半成品"**：准确率远低于基线（都市 45.9% vs 81.2%，西幻 12.5% vs 53.8%）
3. **历史改动总体有效**：置信度流程优化累计提升 +41.2%，但仍有优化空间
4. **主要问题是噪声过滤和名称归一化**：非人物 ARG0、修饰语、头衔后缀是三大瓶颈
5. **连续对话识别是最大瓶颈**：占所有错误的48%，需要专项优化

### 8.2 建议

1. **优先实施方案1+2**：解决非人物 ARG0 和修饰语问题，这是最大收益方向
2. **西幻需要专项优化**：头衔归一化对西幻尤为重要
3. **保留原始名作为别名**：归一化后的核心名作为主名，原始名作为别名，提高匹配召回率
4. **连续对话逻辑需要全新设计**：基于旁白边界的连续对话块识别，而非简单的轮换规则
5. **频次过滤存入战略储备库**：待角色库规模扩大后重新评估
