小说转有声书 · 智能解析引擎 — 项目执行基线 V1.0

一、项目定义与目标

1.1 项目名称

Novel-TTS-Engine（小说转有声书智能解析引擎）

1.2 核心目标

开发一个纯本地运行、低运行时内存消耗的桌面软件，将原始小说文本自动解析为结构化的分角色剧本，为有声书制作提供一键式预处理。

1.3 核心输出

每句话包含以下元数据的 JSON 结构化文件，可直接对接 TTS 引擎：

· 内容类型（对话/旁白/拟声词）
· 说话人（角色ID）
· 情绪标签（怒/喜/悲/惊/惧/中性）
· 语速、语气参数

---

二、核心设计原则

原则 说明
纯本地运行 所有模型、词典打包进安装包，运行时零网络依赖
低运行时 RAM 目标峰值 < 3GB，8GB 机器流畅运行
安装包从宽 不超 2GB 即可
规则优先，统计兜底 确定性场景用规则（~70%），模糊场景用轻量 ML 模型（~30%）
半自动辅助 自动解析完成 80%，用户可手动修正且修改永不丢失
前端友好 支持章节范围选择、随时中断/续接、进度回溯

---

三、技术选型

3.1 原型验证期（当前阶段）

层面 选型
语言 Python 3.10+
虚拟环境 uv（替代 pip+venv）
后端框架 FastAPI（RESTful API，自动生成文档）
前端框架 Streamlit（替代 Gradio，配置禁用遥测）
数据库 SQLite（内置，零依赖）
AI 编程助手 Trae / Cursor（氛围编程辅助）
环境容器 Dev Container（可选）

3.2 成熟期（桌面版发布）

层面 选型
后端 FastAPI（本地 localhost，不变）
前端 TypeScript + Electron
打包 PyInstaller 整合为单一 exe

3.3 不引入的组件

· Cloudflare / Vercel（纯本地项目不需要）
· 任何大语言模型 API（违背离线原则）

四、预置模型清单

组件 选型 体积 用途
HanLP 完整离线版 300MB 分词、NER、词性标注、句法分析
词向量 FastText 中文完整版 1GB 角色上下文向量化
对话分类器 FastText（自训练） 5MB 对话/旁白分类
说话人 L2 BGE-small（ONNX） 100MB 语义相似度排序、对话边界检测
拟声词库 JSON 白名单 <1MB 拟声词识别
情绪兜底 朴素贝叶斯 <1MB 情绪分类兜底
数据库 SQLite <10MB 角色库、进度、编辑持久化

总模型体积：约 1.4GB
运行时 RAM 峰值：约 2.5–3GB（含 Python 运行时）

六、流水线解析流程

```
原始文本
  → [分章] → 正则匹配章节标题
  → [基础 NLP] → HanLP：分词、词性标注、NER、句法分析
  → [对话/旁白分类] → 规则 + FastText 分类器
  → [拟声词识别] → 三重判定（词性 o + 正则 + 词库）→ 标注 sfx
  → [角色库与说话人匹配] → SQLite + 四级匹配（别名/标准名/向量/活跃度）+ BGE-small L2
  → [情绪标注] → 规则（六种基础情绪）+ 朴素贝叶斯兜底
  → [结构化输出] → JSON（含 type/speaker/emotion/speed/tone）
```

七、前端交互接口（RESTful API）

端点 方法 参数 功能
/api/analyze POST start, end, force 分析指定章节范围
/api/pause POST 无 当前章完成后暂停
/api/progress GET 无 返回各章状态列表
/api/reset_chapter POST chapter_id, reset_locks 重置章节
/api/edit_sentence POST chapter_id, sentence_index, data 手动修改句子
/api/edit_character POST character_id, data 手动编辑角色
/api/add_sfx_word POST word 添加拟声词
/api/export GET chapter_id(可选) 导出 JSON / SSML

八、开发阶段

阶段 内容 预估时间 核心产出
一 骨架搭建 + 选型验证 2–3天 分章、分词、NER、句法分析走通；BGE-small 资源评估完成

五 情绪标注 + TTS 导出 2–3天 情绪标签、语速语气参数、导出 JSON
六 UI 打磨与发布 按需 完整桌面应用

总预估：核心功能约 15–20 天

九、项目执行规则（规则 V2.0 摘要）

1. 原子化任务：每个任务点不可再分，拥有明确状态（待开始/进行中/已完成/已审核/阻塞中）
2. 依赖强校验：上游任务非“已审核”状态，AI 必须停止并报警
3. 里程碑准出：每阶段须达成预设的验收标准，才能开启下一阶段
4. 文档双向绑定：需求文件与任务文件通过编号互相引用
5. 变更流程：新需求须生成“变更提案”，用户批准后才可修改文件
6. 过程可见：AI 执行前须简述意图、依赖、方法、预期产出
7. 最小化范围：严禁“顺手优化”其他模块
8. 用户绝对主权：“停止”、“错了”等关键词触发，AI 必须切换为咨询模式
