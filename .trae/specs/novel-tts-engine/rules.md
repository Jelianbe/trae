# Novel-TTS-Engine - 项目规则

## 1. 任务与依赖

### 1.1 原子化与状态
- **规则内容**: 任务清单中的每个任务点必须是不可再分的原子操作。每个任务点拥有明确状态：[待开始]、[进行中]、[已完成]、[已审核]、[阻塞中]
- **生效条件**: 
  - 当编辑 `tasks.md` 文件时自动生效
  - 当任务状态发生变更时自动验证
  - 状态值必须严格匹配上述五种之一，否则拒绝保存

### 1.2 依赖锁定
- **规则内容**: 开发一个任务时，如果状态检查发现它依赖的"上游任务"不是 [已审核] 状态，AI 必须立刻停止，并向你报警："任务[下游任务]依赖的上游任务[上游任务]状态为[未完成]，无法启动。"
- **生效条件**: 
  - 当尝试将任务状态从 [待开始] 变更为 [进行中] 时触发检查
  - 自动扫描 `Depends On` 字段中引用的所有任务
  - 若上游任务状态非 [已审核]，立即阻止状态变更并报警

### 1.3 里程碑
- **规则内容**: 在每个开发阶段结束，必须设置一个里程碑节点。该节点是阶段内所有核心任务点 [已审核] 的集合。只有达成里程碑，才能开启下一阶段。
- **生效条件**: 
  - 当阶段内所有核心任务状态变为 [已审核] 时自动触发里程碑检查
  - 尝试启动下一阶段任务时自动验证上一阶段里程碑状态
  - 里程碑未达成时阻止下一阶段任务启动

## 2. 开发与审核

### 2.1 准出标准（DoD）
- **规则内容**: 每个阶段开始前都必须定义完成标准。没有标准，不得开发。
- **生效条件**: 
  - 阶段启动前必须检查该阶段的 DoD 定义是否完整
  - 每个阶段的 DoD 必须包含至少 3 条可验证标准
  - DoD 未定义或不完整时阻止阶段启动

### 2.2 全流程文档化
- **规则内容**:
  1. 逻辑解释：为什么选这个算法，数据结构这样设计的理由，用简洁的注释或一个 decisions.md 文件记录
  2. Bug调试记录：任何调试时间超过15分钟的Bug，必须在 docs/bug_tracking.md 文件中记录："Bug现象 - 定位过程 - 最终原因 - 修复方案"
- **生效条件**:
  - 代码提交时检查关键算法和数据结构是否有注释或决策记录
  - 检测到调试时间超过15分钟的问题时自动提示记录到 bug_tracking.md
  - PR 合并前检查 docs/bug_tracking.md 是否包含相关记录（如有超过15分钟的调试）

## 3. 需求与变更

### 3.1 双向绑定
- **规则内容**: 需求文件 requirements.md 和任务文件 TASKS.md 之间通过编号（如 BR-004、T-003）互相引用。确保能随时知道一个功能是为哪个需求服务的。
- **生效条件**:
  - 新增或修改任务时检查是否包含需求编号引用
  - 新增或修改需求时检查是否有对应任务引用
  - 需求或任务删除时检查是否存在未清理的引用关系

### 3.2 文档同步准则
- **规则内容**: 一旦代码逻辑发生改变，必须检查这种改变是否影响到需求或任务。如果是，必须将更新文档作为变更的一部分，严禁先改代码后补文档。
- **生效条件**:
  - 代码提交前检查是否涉及需求或任务的变更
  - 若涉及变更，强制要求同步更新相关文档
  - 文档未同步时阻止代码提交

### 3.3 变更流程
- **规则内容**: 当发现问题需新增需求，必须先查询 requirements.md。确认是新需求后，生成一个"变更提案"，提案须包含对新需求的说明和插入项目流程的具体位置。只有在批准后，才能修改对应文件。
- **生效条件**:
  - 检测到新需求请求时自动查询 requirements.md 确认是否已存在
  - 确认新需求后自动生成变更提案模板
  - 提案未获批准时阻止修改任何相关文件

## 4. 协作与行为准则

### 4.1 过程可见（增强）
- **规则内容**: AI在执行任何复杂操作时，都需要在代码输出前，先用自然语言简要说明：
  - 意图：准备做什么？
  - 依赖：依赖于已经达成的哪个共识或哪个文件？
  - 方法：打算用哪个工具/算法/代码结构？
  - 预期产出：完成后会产生哪些文件，改动哪些函数？
- **生效条件**:
  - 执行需要修改多个文件的操作前触发
  - 执行涉及核心逻辑变更的操作前触发
  - 执行可能影响项目结构的操作前触发

### 4.2 用户主权（兜底条款）
- **规则内容**: 用户拥有所有决策的最终否决权。一旦用户说出"停止"、"错了"、"换方法"等关键词，AI必须立刻停下当前自动化流程，并切换为纯咨询模式，与用户共同分析问题，不得固执地继续执行。
- **生效条件**:
  - 实时监测用户输入内容
  - 匹配到停止关键词时立即中断当前操作
  - 中断后自动切换为咨询模式，等待用户进一步指示

### 4.3 最小化范围（强制）
- **规则内容**: 除非任务明确要求重构，否则AI在修改一个模块时，严禁以"顺手优化"为由，去修改其他未在任务中列出的模块。保持每次变更的影响范围绝对可控。
- **生效条件**:
  - 执行修改操作前检查是否在任务定义的范围内
  - 检测到超出任务范围的修改时自动阻止
  - 需要额外修改时必须先更新任务定义或获得用户批准

### 4.4 "记忆"强化
- **规则内容**: 在每个阶段结束时，AI需要为用户生成一个简短的阶段小结。
- **生效条件**:
  - 阶段里程碑达成后自动触发
  - 小结内容包含：阶段目标、完成情况、关键决策、遗留问题、下一阶段计划

## 规则优先级

1. **最高优先级**: 用户主权条款（4.2）- 任何时候用户指令优先于所有规则
2. **高优先级**: 依赖锁定（1.2）、最小化范围（4.3）- 保障项目稳定性
3. **中优先级**: 原子化与状态（1.1）、里程碑（1.3）、准出标准（2.1）- 保障流程规范
4. **常规优先级**: 全流程文档化（2.2）、双向绑定（3.1）、文档同步（3.2）、变更流程（3.3）、过程可见（4.1）、记忆强化（4.4）- 保障质量与协作
